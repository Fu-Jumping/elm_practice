## 范围与工程基线

本版本以课程要求文档和老师课堂口径为主要依据。

以下内容分为三种口径：

- **课程基础范围**：三周课程实践、Git 过程留痕、TDD、前后端分离、RESTful 接口、基础功能、需求变更后的新增测试与回归、架构重构和组间交叉验收。
- **本组执行基线**：阶段 1 六类能力定义为课程基础 P0；用户端移动 H5、商家端桌面 Web 后台与后端在同一个 Git 仓库内按目录各自独立工程开发（frontend/user-h5/、frontend/merchant-admin/、backend/），商家端技术栈为 React 18 + Vite + Ant Design 5（桌面优先 ≥1280px，不做移动端）；登录状态暂采用服务端 Session + Cookie；新接口统一使用 `/api/v1` 资源模型；模拟支付、库存一致性、配送中状态和跨端订单处理作为基础 P0 完成后的团队扩展。
- **待确认项**（2026-09-10 复核，两条结案、一条改待定）：Spring Boot/MyBatis 精确版本**已结案**——Spring Boot 3.5.5 + MyBatis Spring Boot Starter 3.0.4（Java 17，以 `backend/pom.xml` 为准）；数据库选型**已结案**——MySQL 8（测试库 `elm_practice_test`，见 `docs/project/运行说明.md` §4.5）；**阶段 2 实际变更内容改为按「待定」跟踪**——负责人 2026-09-10 判断老师大概率不发布，不作为开发前置阻塞，变更到达时仍按“先补失败测试再改代码”响应；最终材料的精确时间仍待课程通知。本组第二阶段范围决议已于 2026-09-09 落定（除平台管理员外全部 P1/P2 纳入本期，见 §6.1.2 与版本记录 v1.1）；平台管理员为**已砍项**，不制作页面、接口、数据和测试。SRS 正式模板和提交格式已于 2026-09-06 按老师课堂口径确认（只描述需求、不涉及技术实现、非专业人士可读），交付版见 `docs/SRS.md`，工程口径见 `docs/SRS-工程版.md`。

阶段 1 的课程基础 P0 只覆盖：用户注册/登录/个人信息、商家注册与开店/关店、店铺列表/详情/状态、商品管理/分类/列表/详情/价格/库存、购物车增删改查、基础订单创建/状态查询/订单列表。支付、复杂优惠、库存扣减事务、商家接单推进、评价、消息、经营统计和骑手配送不纳入基础 P0，统一作为团队扩展；**阶段 2（2026-09-09 起）除平台管理员外，全部 P1/P2 扩展已纳入本期开发，详见 §6.1.2**。

# 2. 产品背景

## 行业与课题背景

本项目以"用户端移动 H5 + 商家端桌面 Web 后台"的外卖平台为统一业务对象，做成一个能独立运行、能演示、能验收的课程作品。重点是把需求写清楚，方便前后端开发、数据库落地和测试验收。

外卖场景具有角色清晰、数据关系完整、订单状态变化明显的特点，既能展示前端页面、状态和接口调用，也能展示后端分层、数据库、事务、权限、联调和部署。项目保留用户端与商家端，并以“用户下单、订单保存、商家处理、用户查看状态”为核心业务链路。

本文重点是把课程项目写清楚，方便开发和验收。所有完成结论都必须能在源码、接口响应、数据库记录、测试结果或课程材料中找到证据。

## 需要先说清楚的地方

在整理课程要求、课堂口径和设计稿后，需要先统一下面几件事：

- 课程基础范围只到六类能力，字段、交互、状态和异常要补齐，不能只靠页面数量判断完成。
- 基础闭环先做，支付、评价、消息、统计和配送都放在基础功能后面。
- 订单金额、库存和状态要有统一规则，不能前端、后端各算各的。
- 后端、数据库、测试和部署要单独写清楚，避免只写页面不写系统。
- PRD、SRS、接口契约和架构设计要分工明确，别混成一份大文档。

这里只写本项目需要实现和检查的内容；没有实现的内容标为待完成或可选。

## 为什么现在做

课程结项不仅检查页面是否能打开，还要说明需求、系统设计、编码实现、数据库、测试、部署和小组分工。尽早形成可验收的需求标准，可以：

1. 让产品、前端、后端、数据库、测试和联调人员按同一个基础范围与数据标准工作；
2. 先完成六类基础能力和 TDD 证据，再承接需求变更或本组扩展，避免页面很多但核心功能无法验收；
3. 让 PRD、SRS、接口契约、架构设计、建表脚本、测试记录、报告和演示互相印证；
4. 让 RESTful 接口、分层架构和统一校验成为可检查的工程边界，降低需求变更时的返工成本。

### 问题及分析

按"问题—证据—影响—对策"逐项列出，证据均为可核查的工程事实（页面数、规则数、状态取值、模块数）。

#### 2.4.1 问题 1：基础范围还不够细

- **现状**：课程基础范围给出的是模块和操作级需求，页面字段、状态取值、交互规则和异常处理还需要补齐。
- **影响**：如果不把细节写清楚，大家会按自己的理解实现，最后页面、接口和测试都对不齐。
- **对策**：本文用页面矩阵、功能说明、状态规则和原型说明四层内容，把需求写到可以直接开发、直接验收的程度。

#### 2.4.2 问题 2：双端状态要先定好

- **现状**：基础范围要求订单创建、列表和状态查询；商家推进订单及跨端同步属于团队扩展，已于 2026-09-09 决议纳入本期实施。
- **影响**：如果不区分基础状态查询和扩展状态推进，前后端会对状态责任理解不一致。
- **对策**：基础 P0 先保证订单创建、列表和状态查询；阶段 2 按 §7.6 统一状态流转规则（含取消状态）。

#### 2.4.3 问题 3：金额和库存规则要统一

- **现状**：基础订单需要明确商品单价、数量、地址和订单状态；优惠、库存和支付状态要单独定规则。
- **影响**：如果基础阶段把所有复杂规则都塞进去，容易把扩展内容误当成必做内容。
- **对策**：基础 P0 先按商品单价 × 数量和必要配送信息处理；复杂优惠和支付规则作为团队扩展单独说明。

#### 2.4.4 问题 4：文档要分工，不要混写

- **现状**：产品、前端、后端、数据库、测试和联调都要并行，但每一条线关心的内容不一样。
- **影响**：如果一份文档又写产品、又写接口、又写代码，最后很容易互相打架。
- **对策**：本文只写产品范围和用户可见行为；SRS 写系统要实现的行为和验收条件；接口契约写 RESTful 请求/响应；架构设计写模块和数据流。四份材料互相引用，但不重复复制整张接口表。

#### 2.4.5 问题 5：验收要看完整结果

- **现状**：验收会同时看需求、系统设计、编码、测试和部署。
- **影响**：只交代码不够，文档和演示也要能对上。
- **对策**：P0 先保证完整流程可以演示，扩展功能放在后面；目标只按实际做出来的功能检查。

#### 2.4.6 问题 6：页面完成不等于系统完成

- **现状**：一个页面能打开，只说明前端有展示，不说明后端、数据库和测试已经完成。
- **影响**：只看页面容易把演示当完成，答辩时也解释不清数据来源、库存、权限和订单状态。
- **对策**：完成度拆成前端、后端、数据库、联调、测试、部署和课程材料七个维度，每一项都单独留证据。

#### 2.4.7 问题 7：新增模块可能扩大页面范围，却没有形成新的技术证明

- **现状**：消息、评价、优惠、统计、取消订单、配送和图片上传都可能成为扩展内容（平台管理员已于 2026-09-09 决议砍掉）。
- **影响**：如果只增加页面，不补数据、接口、业务规则和验收用例，扩展内容会挤占 P0 时间，也无法证明系统能力。
- **对策**：扩展模块按“课程价值、实现难度、前后端工作量和展示效果”排序；P0 完成后按 2026-09-09 决议实施除平台管理员外的全部 P1/P2，每个模块都必须同时具备接口、数据、测试和页面证据。

### 解决思路

#### 2.5.1 方向一：先打通 P0 主流程，再扩展宽度

用户端以"注册/登录→浏览店铺与商品→查看商品详情→加购→创建订单→查看订单"为基础主线，基础 P0 先整条可验收；商家端以"注册→开店/关店→维护商品与店铺"为基础管理主线。基础功能稳定后，按 2026-09-09 决议承接除平台管理员外的全部本组扩展（模拟支付、订单推进、跨端同步、优惠、评价、消息、统计、取消、配送、图片上传与设置/FAQ 等）。

#### 2.5.2 方向二：两边共建一套状态规则，同步靠数据自动完成

基础订单状态、商品上下架和营业状态统一走数据与接口约定，页面只做呈现与操作入口。若实施订单推进扩展，用户端与商家端再基于同一订单记录完成状态同步，不为演示写死跳转。

#### 2.5.3 方向三：真实工程版为主

真实工程版承载页面、状态和接口联调，是本次课程的正式实现；不制作静态页面，课程展示与截图一律以真实工程为准。

#### 2.5.4 方向四：接口约定先行，前端演示数据可切换

后端项目独立于前端工程开发；前端先按接口约定写好转换代码，用演示数据完整演示，真实接口不可用时自动切回演示数据；正式联调时再关闭自动切换，让接口问题尽早暴露。此举把"联调风险"提前到日常开发阶段发现。

#### 2.5.5 本项目差异化亮点

- **基础闭环可验收**：六类基础能力均有明确的页面行为、接口行为、数据结果和测试场景。
- **接口约定先行**：新接口统一采用资源导向 URI、HTTP 方法、标准状态码和统一响应；详细字段由接口契约维护，前端通过适配层调用。
- **架构适配变化**：业务规则集中在后端 Service，前端不承担最终校验；需求变更优先新增测试和局部修改，减少对已有功能的影响。
- **真实工程统一展示**：真实工程版承载真实状态与接口联调；展示与截图一律使用真实工程页面，不制作静态页面。
- **课程过程证据链**：需求、测试、实现、接口、数据库、联调和答辩材料保持可追溯，完成状态以实际证据为准。
- **扩展模块不只做页面**：选定的扩展必须同时具备业务规则、接口、数据、测试和可解释的演示结果。

#### 2.5.6 方向五：前后端独立工程，统一总说明与接口契约

前端与后端以独立工程协作（同一仓库分目录管理、独立进程部署）；后端按 Java 体系选择可执行的 Web 框架和数据库，具体版本由后端同学确认。新接口统一以 `/api/v1` 为版本前缀，按资源设计路径，并在接口契约中维护请求、响应、状态码和错误结构。PRD 只保留产品边界，内部类结构和完整接口表分别由架构设计、接口契约维护。

#### 2.5.7 方向六：真实闭环优先于功能数量

基础 P0 先完成用户、商家、店铺、商品、购物车和基础订单六类能力。阶段 1 结束后，2026-09-09 决议将除平台管理员外的全部 P1/P2 扩展纳入本期：模拟支付与库存一致性、商家订单推进与跨端同步、优惠与统一计价、评价与商家回复、消息、搜索排序分页、收藏、会员、红包、规格、取消、配送、图片上传与设置/FAQ；商家端桌面 Web 后台为 P0 载体，不属于扩展。Mock 只能证明前端演示，不能作为真实接口验收结果。

## 角色与入口

| 角色       | 入口                                                 | 说明                                                                                                                      |
| ---------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 用户       | 登录/注册页默认用户模式                              | 演示账号 User A（userA）、User B（userB），密码 123456                                                                    |
| 商家       | 桌面 Web 后台登录/注册页（frontend/merchant-admin/） | 支持商家注册、注册即自动建店（初始状态 CLOSED）、店铺开店/关店/临时闭店；固定 m002 可作为种子演示账号，但不能替代注册能力 |
| 平台管理员 | 不实施（2026-09-09 决议砍掉）                        | 平台管理员已砍掉，不制作页面、接口、数据和测试，不作为交付内容                                                             |

用户端与商家端分别实现登录界面（移动 H5 与桌面 Web 后台），主题色一致，角色由入口和后端身份共同决定。当前团队方案采用服务端 Session + Cookie 保存登录状态；这是实现选择，不作为外部硬性指定。用户只能访问自己的购物车和订单等资源，商家只能管理绑定店铺的数据。平台客服不在正式范围内，“联系商家”仅表示用户与订单商家的会话。

## 系统架构与项目边界

全流程项目采用前后端独立工程（同一仓库分目录管理、独立进程部署）+ 统一总说明：

| 层级           | 默认技术与职责                                                                                                                                    | 当前状态               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| 用户端前端     | Vue 3、Vite、Pinia、Vue Router、Axios；负责界面、输入检查、状态展示和接口调用                                                                     | 需要新建前端实现       |
| 商家端前端     | React 18、Vite、Ant Design 5；桌面 Web 后台（frontend/merchant-admin/），桌面优先 ≥1280px，不做移动端；复用同一套`/api/v1` 商家接口            | 需要新建前端实现       |
| 前端接口适配层 | 用户端：接口端点集中表、字段归一化与模式切换（工程内 services 层）；商家端：merchant-admin 工程内独立接口适配层；负责端点集中、字段转换和接口切换 | 需要新写               |

默认数据流：

`用户/商家操作 → 用户端 Vue 页面与 Store、商家端 React 页面与状态 → Axios 接口适配 → Controller → Service 规则与事务 → DAO/Repository → 数据库 → 统一响应 → 页面更新`

后端和商家端桌面后台代码不得写进用户端前端工程目录（frontend/user-h5/）；各工程在仓库根目录按 frontend/user-h5/、frontend/merchant-admin/、backend/ 和 docs/ 分目录管理。最终课程包采用用户端前端、商家端桌面后台、后端、数据库和文档等交付单元；具体框架版本和启动方式由小组在架构设计与运行说明中确认。

## 用户端主流程

1. 用户注册或登录后进入首页；个人信息可以查询和修改。
2. 首页按定位展示店铺，分类入口进入店铺列表，点击店铺进入详情。
3. 店铺详情展示店铺状态、商品分类、商品列表、商品详情、价格和库存。
4. 用户选择商品加入购物车，在购物车中查询、增加、减少或删除商品。
5. 用户在确认页填写订单所需信息并创建订单，系统返回订单结果。
6. 用户在订单列表和订单详情中查询订单状态。

以上是课程基础 P0 主线。模拟支付、商家状态推进、跨端同步、评价、消息、优惠、搜索、收藏、会员、红包、规格、取消与配送等扩展按 2026-09-09 决议在基础主线之后全部实施（平台管理员砍掉）。

## 商家端桌面后台

商家端载体为桌面 Web 后台：技术栈 React 18 + Vite + Ant Design 5，位于 frontend/merchant-admin/，桌面优先 ≥1280px，不做移动端；复用后端同一套 `/api/v1` 商家接口，后端零改动。

1. 商家注册后自动建立并绑定店铺（初始营业状态 CLOSED），登录后维护开店、关店和临时闭店状态。
2. 商家维护商品、商品分类、价格、库存和上下架信息。
3. 用户端可以读取店铺、商品和营业状态的最新结果。

商家端一期（P0 载体）页面为：商家登录/注册、店铺设置（开店/关店/临时闭店）、商品列表与商品新增/编辑表单、分类管理、订单列表与订单详情；商家订单状态推进为已选 P1 扩展（演示高光），在订单页面内完成。按 2026-09-09 决议，原“二期不做”的运营概览、优惠配置、评价管理与回复、消息列表与聊天详情、数据统计、规格维护和联系顾客**一并纳入本期**，与用户端 P1 形成双端闭环。固定 m002 仅作为种子演示店铺。

## 数据与接口策略

- 开发早期和前端独立演示可使用本地演示数据（`src/mocks/**`）；全流程验收必须启用真实接口模式并关闭自动回退，避免接口失败被 Mock 掩盖。
- 接口路径集中在 `src/services/api/endpoints.ts`，页面层不直接拼路径；后端返回字段经 `src/services/normalizers.ts` 做格式转换。
- 新接口统一采用 RESTful 资源导向 URI、正确的 HTTP 方法、标准状态码、统一 JSON 响应和 `/api/v1` 版本前缀；完整请求字段、响应字段和错误码由接口契约维护，PRD 不复制接口表。
- 前后端分离：前端负责交互、展示和即时检查，后端负责最终业务校验、身份权限、数据归属和状态规则；页面层不直接拼接接口路径。
- 基础订单由后端校验商品、数量、订单信息和资源归属；库存事务、并发保护、模拟支付和状态推进属于本期实施方案（2026-09-09 决议），细节由 SRS 工程版、接口契约和测试固定。
- 当前团队认证方案为服务端 Session + Cookie，属于技术选择，不作为外部硬性要求；若后端方案调整，只维护一套最终契约。
- 演示固定数据：5 家商家（老王小店 m001、肯德基宅急送 m002、麦当劳 m003、老胖烧烤 m004、元盛居火锅 m005），主演示商家 m002；点餐分类 10 类。固定数据用于演示，不能替代商家注册验收。

# 7. 具体功能说明

## 7.1 账号与角色

- 登录页默认用户模式，输入账号+密码检查后进入首页；演示账号仅用于稳定演示。
- 用户注册页字段：账号、密码、昵称、性别；注册成功返回登录页并可立即登录。
- 商家注册页字段由接口契约确定最小集合；注册成功即自动创建并绑定店铺，店铺初始营业状态统一为关闭（CLOSED），商家开店后用户端才可下单。
- 固定 m002 肯德基宅急送账号可以作为种子演示数据，但不能替代商家注册、开店和关店能力。
- 用户与商家的登录状态和权限互相独立：用户身份不能进入商家管理接口，商家身份不能访问其他用户的地址和订单。

## 7.2 首页与搜索

- 首页自上而下：定位与搜索区、点餐分类宫格（10 类）、活动/权益区、推荐商家卡片（评分、月售、起送、配送费、距离、促销标签）。
- 商家列表支持排序：销量、距离、评分，排序切换后列表刷新。
- 搜索：输入关键词返回商家汇总（店名匹配）与商品汇总（商品名匹配）；支持搜索历史与热门词，清空历史可删除。关键词搜索、搜索历史与热门词为 P1 本期实现项：后端支持商家名、商品名和分类条件查询，排序取值综合/销量/距离（2026-09-09 决议：距离取种子数据固定 `distanceKm`，不引入地图与定位；综合排序按"销量优先、评分次之"，不做加权公式），分页参数 `page`/`size` 由接口契约统一（默认 `page=1&size=10`），页面不自行过滤真实数据。
- 无数据提示：无搜索结果时展示"没有找到相关商家/商品"提示与返回首页入口。

## 7.3 商家详情与购物车

- 商家详情顶部为商家信息（名称、评分、月售、地址、公告、促销标签），下方为评价入口与点餐区。
- 点餐区：左侧分类栏（热销/套餐/汉堡炸鸡等），右侧对应商品列表；点击分类栏切换右侧列表。
- 商品项展示：名称、说明、价格、库存和上下架状态；会员价、促销标签和规格为本期实现项。
- 商品详情可展示规格选项（如"中杯/大杯"）和数量；规格价差、加料和多规格购物车行随规格扩展本期实现，具体字段由接口契约确定。
- 购物车栏固定在底部：展示购物车内商品数、合计金额、结算按钮；点击展开购物车弹层，可步进调整数量（减到 0 移除该行）。
- 购物车按商家隔离；基础 P0 按商品行合并数量，同一商品不同规格分行（cartLineId）随规格扩展本期实现。
- 店铺休息或未营业时，结算/加购入口禁用并提示。

## 7.4 确认订单与优惠计算

确认订单页自上而下：订单所需收货信息、商品清单（含数量，可步进）、备注输入、金额明细、提交按钮。红包选择与优惠明细为本期实现范围。

基础 P0 金额规则：后端根据当前有效商品单价和购买数量计算商品小计，并返回订单金额；前端只做展示与输入检查，不得把前端计算结果作为最终金额。订单金额构成（2026-09-01 评审决议，2026-09-07 修订展示口径）：实付金额 = 商品小计 + 打包费（每单固定 ¥2.00，演示口径，由后端计价并随订单快照保存），基础 P0 不计配送费；优惠计价启用后按本节扩展顺序把固定配送费与配送费优惠计入最终金额（配送费默认 ¥3.00，演示口径，可由店铺配置，未配置按 0）；用户端确认订单页金额明细展示**商品小计、打包费、配送费与实付金额四行**（配送费为 0 时仍显示该行，金额为 ¥0.00；商家端订单详情金额汇总同口径）（2026-09-09 决议：配送费默认 ¥3.00 计入实付并写入金额快照字段 `deliveryFee`；修订原因：原"不单独列出打包费行"致金额构成不可见，被负责人误判为漏计配送费）。

优惠计价规则（2026-09-09 决议纳入本期，计算顺序固定，金额以后端结果为准）：

1. 商品小计 = Σ(商品单价 × 数量)，单价含规格价差；会员购买时，配置了会员价的商品按会员价计价，未配置会员价的商品沿用基础价；
2. 店铺满减：满足门槛时取最大满足的阶梯规则（如满 20 减 2、满 40 减 5）；
3. 新客立减：仅对店铺新用户首单生效；
4. 配送费：固定配送费，配送费优惠（免配送费券/免配送门槛）只作用于配送费；
5. 会员折扣：按折扣率作用于商品小计，**与会员价不叠加**（已按会员价计价的商品不再重复打折，仅未配置会员价的商品适用会员折扣）；
6. 用户红包：满足门槛（threshold）且在适用范围（全场/指定商家）内可用，一单一红包；
7. 最终金额 = 商品小计 − 满减 − 新客立减 − 红包 − 会员折扣 + 配送费 − 配送费优惠 + 打包费（¥2.00），且不小于 0。金额构成与快照字段以接口契约为准。

演示数值口径（2026-09-09 决议默认，写入种子数据与测试基线）：满 20 减 2、满 40 减 5；新客立减 3 元；免配送费门槛 30 元；会员折扣 95 折；红包门槛与适用范围由种子数据定义，一单一红包。数值调整须同步契约、种子数据与测试用例。

检查：订单所需信息缺失时提交按钮禁用并提示补充；商品已下架、库存不足或店铺不可用时提示修正；金额与后端结果不符时以后端为准。

## 7.5 支付与支付反馈（本组扩展）

- 基础 P0 创建订单后可以直接进入订单结果页；支付扩展已纳入本期，创建订单成功后进入支付页展示订单号、金额和模拟支付方式。
- 支付页为前端模拟：点击"确认支付"模拟成功进入支付成功页（展示订单号、预计送达、查看订单/返回首页），模拟失败进入支付失败页（提供重试支付与返回订单列表）。
- 支付成功后更新订单支付状态；订单进入商家处理流程属于本期扩展范围（2026-09-09 决议），不作为基础 P0 的完成条件。
- 不接第三方支付；后端负责接收模拟支付成功后的状态更新并防重复提交。支付反馈不重复扣库存，库存只在订单创建事务中处理一次。

## 7.6 订单状态规则与跨端同步（本组扩展）

基础 P0 创建订单成功后订单状态即为进行中（PROCESSING），订单可查询但不流转；待支付（PENDING_PAYMENT）、商家推进状态与取消状态属于本组扩展，2026-09-09 决议全部纳入本期。商家订单推进为演示高光；订单状态统一存储在单一状态字段（merchantStatus 已废弃），取值与 `docs/backend/后端接口契约.md` 对齐：

| 订单状态（扩展期） | 用户端展示                                     | 商家端展示 | 触发           |
| ------------------ | ---------------------------------------------- | ---------- | -------------- |
| PENDING_PAYMENT    | 待支付（15 分钟倒计时）                        | —         | 提交订单未支付 |
| PENDING            | 待接单                                         | 待接单     | 支付成功       |
| COOKING            | 制作中                                         | 制作中     | 商家接单       |
| DELIVERING         | 配送中                                         | 配送中     | 商家出餐配送   |
| COMPLETED          | 已完成；未评价时用户端按评价情况展示为"待评价" | 已完成     | 商家完成订单   |
| CANCELLED          | 已取消                                         | 已取消     | 用户取消（未支付或未接单） |

**用户端订单进度时间线：文案 ↔ 状态值映射（2026-09-11 定稿，CHG-003）**

| 时间线文案（用户端） | 订单状态值 | 触发 |
| --- | --- | --- |
| 已下单 | `PENDING_PAYMENT` | 提交订单未支付 |
| 已支付 | `PENDING` | 支付成功（待商家接单） |
| 商家接单 | `COOKING` | 商家接单/制作中 |
| 配送中 | `DELIVERING` | 商家出餐配送 |
| 已完成 | `COMPLETED` | 商家完成订单 |

- **时间线所在页面**：订单详情页（订单跟踪页已于 2026-09-11 并入订单详情，见 CHG-003）；**配送进度不再单设页面**，由本页时间线与配送信息卡表达（CHG-002）。
- **取消订单**：`CANCELLED` **不进入时间线**——订单详情显示「已取消」与取消原因，时间线整体置灰。

> **配送状态的展示口径（2026-09-11 负责人拍板，CHG-002）**：用户端**不设独立配送页，也不单列配送单状态**——配送进度直接由订单状态表达（`DELIVERING` → 配送中、`COMPLETED` → 已完成），订单详情与订单列表**现有的状态区与收货信息即可覆盖**，**无需新增字段、接口或页面**；商家端「出餐/完成」按钮推进订单状态即可。

扩展规则：

- 用户端列表筛选取值：全部/待支付/进行中/已完成/待评价/已取消（`orderStatuses`）。
- 状态只能按顺序更新；后端检查跳过状态的操作（如从待接单直接跳已完成）应拒绝。
- P0 阶段订单固定为 `PROCESSING`（进行中）；支付与推进扩展启用后，**支付成功必须进入 `PENDING`（待接单）**，`PROCESSING` 不再作为支付后的状态。当前后端实现为先置 `PROCESSING`、商家接单后才置 `PENDING`，与本节不一致，需按本节修正（契约待确认清单已登记）。
- 商家端拒单当前只做展示，不作为 P0 真实流程。
- 支付成功、接单、状态更新都不能重复生效，重复请求不能把状态更新两次。
- 订单使用单一状态字段；用户端展示状态由该字段与评价情况计算，“待评价”不是独立存储状态。库存统一在创建订单事务内校验并扣减；支付超时不自动回补库存，属于课程简化规则。状态字段、流转条件和展示映射由接口契约固定。

取消与配送规则（2026-09-09 决议纳入本期）：

- 用户取消：仅 `PENDING_PAYMENT`（未支付）与 `PENDING`（已支付未接单）允许取消，必须记录取消原因，订单进入 `CANCELLED` 并保留订单与明细快照；取消在同一事务内回补库存。`COOKING` 及之后不允许取消。
- 取消不接真实退款与资金处理；用户端取消前二次确认，商家端订单列表与详情出现"已取消"状态与原因。
- **取消入口（2026-09-11 负责人拍板）**：用户端取消入口统一位于**支付页内**——**不与「立即支付」并排**，放在页面内容区，**具体位置以最终设计稿为准**；**订单列表页与订单详情页不提供取消按钮**；取消前弹出「取消订单确认弹层」做二次确认（原因必填）。
- 配送：配送单状态取 `PENDING_DELIVERY`/`DELIVERING`/`DELIVERED`（待配送/配送中/已送达），由商家端在订单详情推进；用户端订单跟踪页只读展示配送信息与状态；不建骑手端，不做地图与实时定位。

> 基础下单流程和扩展跨端同步流程见“产品流程”章节；完整泳道图应在扩展方案确定后补齐。

## 7.7 评价流程（本期实现）

- 无数据提示：无聊天/无通知时显示对应的无数据提示。
- 商家端消息页面随 2026-09-09 决议纳入本期（见 6.17）；消息扩展双端同期实现，用户端与商家端未读分别记录。

## 7.15 认证、角色与资源归属

- 用户登录：账号和密码由后端检查；登录成功建立服务端会话，返回必要用户信息但不返回密码。
- 商家登录：商家账号必须绑定店铺；进入商家端后所有店铺、商品和订单接口都以后端会话中的商家身份为准。
- 前端路由：未登录用户可以浏览首页、商家列表和详情；购物车写入、地址、下单、订单、消息和评价需要用户身份；商家页面需要商家身份。
- 资源归属：用户只能访问自己的地址、购物车、订单、评价和会话；商家只能修改本店商品、设置、优惠并处理本店订单。
- 登录失效：接口返回统一未登录状态，前端保留当前页面地址并跳转登录；登录成功后返回原流程。
- 当前团队方案使用 Session + Cookie；该方案是技术选择。若后端团队基于课程环境选择其他会话方式，只保留一套最终认证契约，并同步修改接口和测试。

## 7.16 订单事务、库存与金额安全（本组扩展）

基础 P0 在创建订单时校验身份、商品、库存并保存订单：下述步骤 1-4 与 7 保持一致，库存扣减在同一事务内完成，但不要求并发条件更新和 409 保护。若实施库存一致性扩展，创建订单的后端步骤固定为：

1. 检查用户身份、地址归属、商家营业状态和购物车归属；
2. 重新查询商品、规格、价格、库存和上下架状态，不直接信任前端金额；
3. 按统一顺序计算商品小计、店铺优惠、会员/红包和配送费；
4. 检查库存，任一商品不足则返回具体商品和可用数量，不创建半成品订单；
5. 在一个事务中保存订单头、订单明细快照、扣减库存并清空当前用户在该商家的购物车；
6. 返回订单对象或订单号，前端进入模拟支付页；
7. 事务任一步失败全部回滚，库存、订单和购物车保持原状。

支付成功、接单、状态推进和取消必须支持重复请求：同一目标状态重复提交返回当前订单，不得再次扣库存、回补库存或跨越下一状态。用户取消订单在事务内回补库存；支付超时未支付仍不自动回补（课程简化口径），两种规则不得混用。前端 `expectedTotal` 只用于提示，最终金额以后端计算为准。本项目不引入生产者/消费者、消息队列或异步库存服务；并发保护以数据库事务和条件更新等课程规模内方案为限。

## 7.17 搜索、统计与加分模块实施边界

- 搜索：本期实现，后端支持商家名、商品名和分类条件查询；分页和排序参数由接口契约统一，不在页面层自行过滤真实数据。
- 真实统计：本期实现，只统计数据库中的有效订单；营业额、订单数、客单价、状态分布和时间趋势必须注明查询范围，不再使用固定演示数值作为完成证据。
- 优惠：由后端保存配置并计算订单金额；超额优惠、负数、非法折扣和过期优惠必须被拒绝或限制到合法范围。
- 评价：完成订单才能评价，一单一评；商家只能回复本店评价，重复回复更新原记录。
- 消息：会话与订单、用户和商家关联；空消息拒绝，未读分别记录用户端和商家端。
- 取消、配送和图片上传：2026-09-09 决议纳入本期（范围确认与工作量评估已完成）；配送只做配送单与状态，不建骑手端、不做地图与实时定位。
- 平台管理员：2026-09-09 决议砍掉，不制作页面、接口、数据和测试，不因设计稿或参考原型存在而纳入。
- **占位口径（2026-09-10 负责人拍板，CHG-001）**：**有真实数据统计的位置一律显示真实值**（来自接口与数据库）；**没有真实统计的位置显示占位内容**，占位与真实内容同款式、点击提示「暂未开放」，且**不得用于经营数据位**——商家端统计、订单金额与优惠明细、红包金额与门槛、评分与评价数等经营位必须来自真实数据，无数据时显示 0 或留空，不使用固定演示数值（与 §8 一致）。

基础 P0 下单主流程：

1. 用户提交账号密码，后端检查用户并建立登录会话；用户可以查询和修改个人信息。
2. 前端从真实接口读取店铺和商品，用户查看商品详情并加入购物车，购物车按用户和店铺隔离。
3. 用户查询、增加、减少或删除购物车商品，确认订单信息后提交创建订单。
4. 后端校验身份、商品、数量和订单信息，保存订单及明细并返回订单结果。
5. 用户在订单列表和订单详情中查询订单状态；失败时前端展示可修正原因。

本组扩展流程：模拟支付、库存事务、商家订单推进、配送中展示和跨端同步在基础流程通过后增加；配送中只作为商家按钮推进的演示状态，不建设骑手系统。

商家处理与跨端同步扩展流程：

1. 商家用已注册或种子账号登录，后端建立商家会话。
2. 商家端查询数据库中属于本店的待接单订单。
3. 商家按制作中→配送中→已完成更新，后端检查商家归属、目标状态和重复请求。
4. 每次合法更新写入数据库；用户端重新查询后显示制作中、配送中或待评价。
5. 商家修改商品上下架、库存、价格或营业状态后，用户端真实接口读取到最新结果；旧购物车在结算时必须重新检查。

评价与消息流程：

1. 用户对属于自己且已完成的订单提交评价，一单一评检查通过后保存数据库。
2. 商家端读取本店评价并回复，用户端重新查询后回显回复内容。
3. 消息模块入选 P1 后，用户发送消息写入会话和消息表，商家端未读 +1；商家回复后用户端未读 +1。

#### 原型说明统一规则

1. **数据来源和默认值**：后端返回的数据必须标出接口来源和字段含义；页面参数必须标出来源；用户填写的内容标为用户输入；只为保证页面第一次打开而使用的数据标为课程演示默认值。金额使用元并保留两位小数，时间统一使用 `yyyy-MM-dd HH:mm:ss`（东八区），数量使用非负整数，空文本不显示为 `undefined` 或 `null`。
2. **加载状态**：首次进入页面显示区域级骨架或加载提示；刷新某个列表时保留已显示内容并在列表区域显示加载状态；提交、删除、切换营业状态和推进订单时，操作按钮显示处理中并暂时禁止重复点击。请求结束后恢复按钮，不能永久停留在加载状态。
3. **空态**：列表没有数据时说明“没有什么数据”和下一步操作，例如“暂无订单，去首页看看”或“暂无商品，新增商品”；空态不是接口错误，也不能用演示数据静默替代真实空结果。
4. **错误状态**：网络失败、超时、服务端错误、未登录、无权限、参数错误、资源不存在和状态已变化要分别处理。能重试的区域提供重试；未登录跳转登录并保留原地址；无权限不显示修改入口；资源不存在返回上一级；提交失败保留用户输入。
5. **校验边界**：前端在提交前做必填、格式、长度和数值范围检查；后端再次检查身份、归属、状态、金额、库存和唯一性。前端按钮是否置灰不能代替后端校验；后端拒绝后页面必须显示可理解的原因。
6. **成功后的同步**：新增、修改、删除、加购、创建订单和状态推进成功后，当前区域立即回显后端返回结果，并刷新受影响的列表、计数、金额或状态；返回其他页面再进入时重新读取，不依赖旧页面缓存。操作失败不得提前修改为成功状态。
7. **并发和重复操作**：同一按钮的重复点击只产生一次请求；商品被下架、库存变化、订单状态被另一端修改时，页面提示“数据已变化，请刷新后重试”，然后重新读取相关数据。用户不能通过修改页面参数访问其他用户或其他商家的数据。
8. **图片和演示数据**：图片加载失败显示统一占位图并保留文字信息；演示数据必须注明为默认展示数据。真实接口模式下接口返回空数组就是空态，不能因为接口失败自动伪装成成功。

P0 页面至少要覆盖以下检查场景：首次加载、空列表、网络失败后重试、未登录、登录失效、无权限、字段缺失、重复提交、资源被删除、店铺关闭、商品下架、库存不足、金额变化、订单状态变化和返回后重新加载。P1/P2 页面沿用同一规则；2026-09-09 决议后全部 P1/P2 页面（平台管理员除外）都要求真实接口、数据与测试证据。

记录边界：

- Mock 模式通过只能证明前端演示链路，不得记为真实后端联调通过。
- 经营统计本期实现，只统计数据库中的有效订单并注明查询范围；没有真实数据时显示 0 或空值，不得用固定演示数值冒充经营结果。
- 没有截图、日志、接口响应或可重复操作步骤的结论，报告中只能写“待验证”。
- 本节的记录字段用于课程验收，不要求在产品代码中新增用户行为采集 SDK、埋点表或统计后台。

### 其他内容

#### 课程汇报主线

建议用以下顺序讲解本项目：

1. 项目以六类基础能力为第一阶段范围，先建立可运行、可测试、可解释的最小闭环。
2. 用户端前端使用 Vue 3、Vue Router、Pinia 和 Axios；商家端使用 React 18、Vite 和 Ant Design 5 桌面 Web 后台。
3. 后端和数据库负责身份、数据持久化、业务校验和接口响应；前端不承担最终业务规则。
4. 通过测试先行、RESTful 契约、分层架构和需求变更回归证明工程质量，再实施已选定的扩展（2026-09-09 决议：除平台管理员外全部 P1/P2 纳入本期）。
5. 通过前后端构建、接口响应、数据库变化、测试、交叉验收和课程材料证明完成程度，不虚构数据。

| CANCELLED      | 已取消；仅未支付（PENDING_PAYMENT）或已支付未接单（PENDING）可由用户取消，记录原因并在事务内回补库存，不接真实退款 |

| 会员价         | 商品对会员展示与计价的单价字段，随会员权益扩展进入商家端商品表单与后端计价 |
| specOptions    | 商品规格选项及对应价差                                                                                                           |
| itemsJson      | 创建订单时传递的商品明细数据                                                                                                     |

#### 明确不做项

- 平台客服、电话客服、智能客服和客服工单；“联系商家”只表示订单用户与商家的聊天。
- 骑手位置、配送地图和真实物流跟踪；简化配送管理已按 2026-09-09 决议本期实施，但只做配送单与状态，不建骑手端、不做地图定位。
- 退款、售后、拒单后的真实资金处理；简化取消订单已按 2026-09-09 决议本期实施，只记录取消状态与原因，不接真实退款。
- 积分体系、积分兑换、真实会员购买或续费。
- 第三方支付、真实扣款和支付安全系统；支付只做前端模拟反馈。
- 复杂 RBAC、多商户组织后台、生产环境监控和真实用户行为采集；用户/商家基础认证和资源归属属于 P0，不能省略。**平台管理员（含商家/商品审核与下架后台）已于 2026-09-09 决议砍掉，不在本期范围。**
- 微服务、消息队列、分布式缓存等超出课程最小闭环的基础设施。
- 把 Java 后端或商家端代码写进用户端前端工程目录（frontend/user-h5/）；后端在 backend/ 独立工程实现，商家桌面后台在 frontend/merchant-admin/ 独立工程实现。
