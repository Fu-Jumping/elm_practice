## 1. 接口总规则

> 本章全部规则为**默认约定**：后端可按实现调整，调整后回写本文即可，前端跟随实现适配。

### 1.1 地址和请求

- 本地服务地址：`http://127.0.0.1:8080`。
- 所有接口路径以 `/api/v1` 开头，例如 `GET /api/v1/stores`。
- 查询条件使用 URL 查询参数；新增和修改使用 JSON 请求体；删除通常不需要请求体。
- 请求和响应统一使用 UTF-8；JSON 接口的 `Content-Type` 为 `application/json`。
- 允许当前前端开发地址跨域访问，例如 `http://127.0.0.1:5173`、`http://localhost:5173` 和 Vite 顺延端口（端口仅为参考，以后端实际放行的开发地址为准）。
- 需要登录的接口从服务端 Session 读取当前用户或商家身份，不接受前端传入的 `userId`、`merchantId` 作为权限依据。

### 1.2 会话

- 登录成功后通过 `Set-Cookie` 写入服务端 Session Cookie；前端请求携带 `credentials`。
- 用户会话和商家会话必须区分角色；用户不能访问商家管理接口，商家不能访问用户的私人地址和订单。
- 未登录返回 `401`；登录成功但角色不匹配返回 `403`。
- 退出登录销毁当前 Session；Session 失效后所有受保护请求都返回 `401`。

### 1.3 统一响应

成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

约定：

- HTTP 状态码表达请求结果，`code=0` 表示业务成功；业务失败使用非零 `code`。
- 列表成功返回数组；没有数据返回空数组，不把空列表当作错误。
- 金额使用数字，单位为元，后端计算后保留两位小数；前端传入的期望金额只用于提示或一致性检查。
- 时间统一使用 `yyyy-MM-dd HH:mm:ss`（东八区），全项目唯一格式；SRS 与本契约一致。
- 布尔值使用 `true/false`；数量、库存使用非负整数。

错误响应：

```json
{
  "code": 40001,
  "message": "商品库存不足",
  "data": null,
  "details": {
    "field": "quantity",
    "reason": "库存最多为 2"
  }
}
```

错误状态最小集合：

| HTTP 状态 | 使用场景 |
| --- | --- |
| `400` | JSON 格式错误、必填字段缺失、字段格式或范围不合法 |
| `401` | 未登录、Session 失效 |
| `403` | 角色不匹配、无权访问资源 |
| `404` | 资源不存在，或资源不属于当前身份时按安全需要统一返回不存在 |
| `409` | 重复注册、状态冲突、库存/金额/版本已变化 |
| `500` | 未预期的服务端错误 |

服务端错误也必须返回 JSON，不能返回服务器默认 HTML 错误页。错误消息应能帮助页面显示可理解的处理建议，但不能泄露密码、数据库细节或堆栈信息。

## 3. P0 用户端接口

### 3.1 用户注册、登录和当前用户

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/v1/users` | 注册用户 |
| `POST` | `/api/v1/auth/login` | 用户登录；请求体中的 `role` 为 `user` |
| `POST` | `/api/v1/auth/logout` | 注销当前会话 |
| `GET` | `/api/v1/me` | 查询当前用户 |
| `PATCH` | `/api/v1/me` | 修改当前用户允许修改的资料 |

注册请求示例：

```json
{
  "account": "13800000002",
  "password": "123456",
  "nickname": "张同学"
}
```

登录请求示例：

```json
{
  "account": "13800000001",
  "password": "123456",
  "role": "user"
}
```

登录成功返回当前用户摘要并建立 Session。账号重复返回 `409`；账号或密码错误返回 `401`；字段不合法返回 `400`。密码不能在响应或日志中返回。

### 3.2 店铺和商品查询

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/v1/stores` | 查询可展示的店铺列表 |
| `GET` | `/api/v1/stores/{storeId}` | 查询店铺详情和营业状态 |
| `GET` | `/api/v1/stores/{storeId}/categories` | 查询店铺分类 |
| `GET` | `/api/v1/stores/{storeId}/products` | 查询店铺商品 |
| `GET` | `/api/v1/products/{productId}` | 查询商品详情 |

`GET /stores` 的可选参数：`keyword`、`categoryId`、`sort`。`sort` 最小取值为 `综合`、`销量`、`距离`，默认 `综合`。列表没有结果返回 `data: []`。

店铺对象至少包含：`storeId`、`name`、`description`、`image`、`rating`、`monthlySales`、`deliveryMinutes`、`startPrice`、`deliveryFee`、`status`。`status` 取 `OPEN`、`CLOSED`、`TEMPORARILY_CLOSED`。

商品对象至少包含：`productId`、`storeId`、`categoryId`、`name`、`description`、`image`、`price`、`stock`、`onSale`。下架商品可以由商家接口查询，但用户端商品列表不得展示为可购买状态。

### 3.3 地址

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/v1/me/addresses` | 查询当前用户地址 |
| `POST` | `/api/v1/me/addresses` | 新增地址 |
| `GET` | `/api/v1/me/addresses/{addressId}` | 查询地址详情 |
| `PATCH` | `/api/v1/me/addresses/{addressId}` | 修改地址或默认状态 |
| `DELETE` | `/api/v1/me/addresses/{addressId}` | 删除地址 |

地址对象至少包含：`addressId`、`contactName`、`contactSex`、`contactPhone`、`region`、`detail`、`label`、`isDefault`。查询只返回当前用户地址；没有地址返回空数组。删除默认地址时，后端自动把剩余地址中最近更新的一条设为默认；没有剩余地址时默认地址为空。

### 3.4 购物车

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/v1/cart?storeId={storeId}` | 查询当前用户指定店铺购物车 |
| `POST` | `/api/v1/cart/items` | 加入购物车 |
| `PATCH` | `/api/v1/cart/items/{cartLineId}` | 修改购买数量（规格信息属于规格扩展） |
| `DELETE` | `/api/v1/cart/items/{cartLineId}` | 删除购物车行 |

加入购物车请求示例（基础 P0）：

```json
{
  "storeId": "m002",
  "productId": "p101",
  "quantity": 2
}
```

基础 P0 购物车行的唯一范围是“当前用户 + 店铺 + 商品”，同一商品重复加购合并数量。规格（`spec`）与加料（`addOns`）字段只在规格扩展选定后启用，届时唯一范围扩展为“当前用户 + 店铺 + 商品 + 规格组合”，同一商品不同规格不能错误合并。后端重新读取商品价格和上下架状态；客户端提交的单价只能作为显示或一致性提示，不能作为计价依据。数量必须大于 0，数量为 0 的修改由前端改为删除请求或由后端返回明确错误。

### 3.5 订单

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/v1/orders` | 从当前用户购物车创建订单 |
| `GET` | `/api/v1/orders` | 查询当前用户订单列表 |
| `GET` | `/api/v1/orders/{orderId}` | 查询当前用户订单详情 |
| `GET` | `/api/v1/orders/{orderId}/items` | 查询订单明细；也可以直接包含在详情中 |
| `POST` | `/api/v1/orders/{orderId}/payment` | P1 模拟支付结果更新 |

创建订单请求示例：

```json
{
  "storeId": "m002",
  "addressId": "da001",
  "remark": "少放辣",
  "expectedTotal": 68.00
}
```

创建订单时后端以当前用户购物车和数据库商品数据为主，重新检查店铺营业状态、商品上下架、数量、库存、起送条件和金额；库存校验与扣减在创建订单事务内完成，并发条件更新与 409 保护属于库存一致性扩展。金额由后端计价：订单实付金额 = 商品小计 + 打包费，打包费为每单固定 `2.00` 元（演示口径），前端传入金额只用于提示或一致性检查。订单必须保存商品快照、地址快照、金额快照和创建时间；金额快照至少包含商品小计、`packagingFee`（打包费）与实付金额，三者满足实付金额 = 商品小计 + `packagingFee`。订单头、订单明细以及需要同步的购物车变化必须在一个事务中完成，事务提交成功后清空该用户在该店铺的购物车行，事务失败时购物车保持原状。

订单使用单一状态字段。基础 P0 只出现 `PROCESSING`（进行中）：创建订单成功即为 `PROCESSING`，订单可查询但不流转。选定模拟支付扩展后增加 `PENDING_PAYMENT`（待支付，创建后 15 分钟内可支付，支付成功进入 `PROCESSING`，超时支付返回 `409`，库存不自动回补）；选定商家订单推进扩展后，`PROCESSING` 细分为 `PENDING`（待接单）→ `COOKING`（制作中）→ `DELIVERING`（配送中）→ `COMPLETED`（已完成）。完整状态机以本契约和小组确认结果为准，SRS 创建后由 SRS 固化。订单列表支持 `status` 查询参数，默认按创建时间倒序。

模拟支付不接第三方支付，不传银行卡或支付平台信息。支付接口只能更新当前用户自己的待支付订单；重复支付请求返回当前结果，不重复扣款或生成订单。

## 4. P0 商家端接口

商家端为桌面 Web 后台（React 18 + Vite + Ant Design 5，位于本仓库 `frontend/merchant-admin/`），复用本契约全部商家接口，后端零改动。所有商家管理接口从当前商家 Session 读取店铺归属，不能信任请求体中的 `storeId` 作为权限依据。

### 4.1 商家账号和店铺

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/v1/merchants` | 注册商家并创建或绑定店铺 |
| `POST` | `/api/v1/merchant/auth/login` | 商家登录；请求体中的 `role` 为 `merchant` |
| `GET` | `/api/v1/merchant/me` | 查询当前商家和绑定店铺 |
| `GET` | `/api/v1/merchant/store` | 查询当前店铺 |
| `PATCH` | `/api/v1/merchant/store` | 修改店铺基础资料 |
| `PATCH` | `/api/v1/merchant/store/status` | 修改营业状态 |

商家注册至少接收账号、密码、店铺名称和联系电话；注册成功即建立店铺，店铺初始营业状态固定为 `CLOSED`（关闭），商家开店后用户端才可见并可下单；账号唯一性和字段格式按小组确认口径执行。营业状态取 `OPEN`、`CLOSED`、`TEMPORARILY_CLOSED`。状态修改成功后，用户端重新查询店铺即可看到最新结果；失败不能提前显示成功。

### 4.2 分类和商品管理

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/v1/merchant/categories` | 查询当前店铺分类 |
| `POST` | `/api/v1/merchant/categories` | 新增分类 |
| `PATCH` | `/api/v1/merchant/categories/{categoryId}` | 修改分类 |
| `DELETE` | `/api/v1/merchant/categories/{categoryId}` | 删除分类 |
| `GET` | `/api/v1/merchant/products` | 查询当前店铺商品 |
| `POST` | `/api/v1/merchant/products` | 新增商品 |
| `GET` | `/api/v1/merchant/products/{productId}` | 查询商品编辑数据 |
| `PATCH` | `/api/v1/merchant/products/{productId}` | 修改商品 |
| `DELETE` | `/api/v1/merchant/products/{productId}` | 删除商品；仅下架状态商品可删除 |
| `PATCH` | `/api/v1/merchant/products/{productId}/availability` | 修改上下架和库存等可售状态 |
| `PUT` | `/api/v1/merchant/products/{productId}/specifications` | 修改商品规格；选定规格扩展后启用 |

分类名称不能在同一店铺重复；删除分类采用阻断式方案：有商品的分类删除请求返回 `409`，提示先处理商品归属，不做静默删除或级联删除。删除商品接口仅允许删除下架状态商品：在售商品删除请求返回 `409` 并提示先下架；删除为物理删除，历史订单因保存商品快照不受影响；删除前前端必须二次确认，后端仍以接口状态校验为准。商品名称、分类、价格和库存必须由前后端分别检查，后端再次检查商品属于当前店铺。库存为 0 时用户端显示售罄并禁止加入购物车。图片上传不在本契约内，若选定图片上传扩展，再补充独立资源接口。

## 6. P1 用户和商家消息、评价与优惠

下列接口只有选定对应 P1 模块后才实现；未选定时页面显示“暂未开放”，不把 Mock 页面当作真实接口交付。

### 6.1 消息

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/v1/conversations` | 查询当前角色可见的会话 |
| `GET` | `/api/v1/conversations/{conversationId}` | 查询会话详情和消息 |
| `POST` | `/api/v1/conversations/{conversationId}/messages` | 发送消息 |
| `PATCH` | `/api/v1/conversations/{conversationId}/read` | 标记当前会话已读 |

会话必须关联订单、用户和商家；“联系商家”只表示订单用户与该订单商家的会话，不建设平台客服。空消息和超长消息返回 `400`；发送失败时客户端保留输入并允许重试。

### 6.2 评价

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/v1/stores/{storeId}/reviews` | 查询店铺评价，可按筛选条件查询 |
| `POST` | `/api/v1/orders/{orderId}/review` | 用户为已完成订单提交评价 |
| `GET` | `/api/v1/merchant/reviews` | 查询当前店铺评价 |
| `PATCH` | `/api/v1/merchant/reviews/{reviewId}/reply` | 商家回复评价 |

同一订单只允许一条评价；商家只能回复本店评价。回复更新原回复，不新增重复记录。评价内容、评分、图片数量和大小由 SRS 固定，服务端再次检查。

### 6.3 优惠和经营概览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/v1/merchant/promotions` | 查询当前店铺优惠配置 |
| `PUT` | `/api/v1/merchant/promotions` | 保存当前店铺优惠配置 |

优惠和统计必须在选定后再写入 SRS 的字段与计算规则。统计没有真实数据时返回 0 或空数组，不能用固定数字证明经营效果。

## 7. 事务、并发和幂等

- 订单创建使用数据库事务，订单头、商品明细快照和购物车变化不能出现半成功。
- 库存扩展采用数据库事务和条件更新或行级锁保护，例如仅在 `stock >= quantity` 时扣减；本项目不引入生产者/消费者、消息队列或异步库存服务。
- 同一按钮的重复点击由前端禁用，后端仍必须通过唯一约束、状态条件或幂等键防止重复写入。
- 商品下架、店铺关闭、金额变化、库存不足和订单状态变化都以提交时后端结果为准。
- 用户和商家查询、修改、删除资源前必须检查身份和归属；不能只依赖 URL 中的编号。
- 发生并发冲突返回 `409`，响应说明“数据已变化，请刷新后重试”，页面重新读取相关数据。

## 8. 联调要求

开发阶段可以使用前端 Mock，但真实联调必须关闭回退：

```powershell
$env:VITE_API_MODE = "real"
$env:VITE_API_BASE_URL = "http://127.0.0.1:8080/api/v1"
$env:VITE_MOCK_FALLBACK = "false"
npm run dev -- --host 127.0.0.1
```

后端每完成一个模块，至少提交以下记录：

```text
接口：
请求方式和路径：
请求参数或请求体：
成功响应：
异常响应及 HTTP 状态码：
数据库影响：
已验证页面：
是否关闭 Mock 回退：
是否与前端联调通过：
```

以下情况不算联调通过：

- HTTP 状态为 200 但返回 HTML 错误页。
- 同一字段或状态在不同接口中含义不一致，且未在契约说明。
- 订单只保存订单头，没有商品和地址快照。
- 购物车按商品编号错误合并了不同规格。
- 商家能读取或修改其他店铺订单、商品或店铺信息。
- 支付、状态推进或重复提交造成重复数据或状态跳跃。
- 页面展示成功，但接口和数据库实际失败。

## 9. 后端 A 实现补充（2026-09-06）

当前 Spring Boot 实现统一返回 `ApiResponse`：成功固定为 `code=0`、`message=success`；错误响应保留 `data=null`，并按需要提供 `details`。实现使用以下业务错误码，HTTP 状态仍是客户端判断请求结果的首要依据：

| code | HTTP | 场景 |
| --- | --- | --- |
| `40001` | 400 | 请求体、必填字段、格式或数值范围不合法 |
| `40101` | 401 | 未登录、Session 失效或凭据错误 |
| `40301` | 403 | 当前会话角色不匹配 |
| `40401` | 404 | 资源不存在或不属于当前身份 |
| `40901` | 409 | 重复注册、库存/状态/金额冲突 |
| `50000` | 500 | 未预期服务端错误（不返回堆栈） |

实现字段补充：订单详情的 `itemSubtotal`、`packagingFee`、`total` 是下单时金额快照，且 `total = itemSubtotal + packagingFee`；订单响应附带 `paidAt`（未支付为 `null`），不再回显请求侧的 `expectedTotal`；购物车响应同时返回 `unitPrice`、`quantity`、`subtotal`；用户和商家对象不返回密码或密码摘要。商家订单查询 `GET /api/v1/merchant/orders` 与 `GET /api/v1/merchant/orders/{orderId}` 按第 5.1 节作为 P0 实现，归属由 Session 中商家店铺确定。

2026-09-06 修复轮补充（后端 A，AI 协助核查后修复）：

- **订单初始状态**：模拟支付扩展已选定，`POST /api/v1/orders` 创建成功即 `PENDING_PAYMENT`（无开关）；15 分钟内 `POST /api/v1/orders/{orderId}/payment` 支付成功进入 `PROCESSING` 并记录 `paidAt`，超时支付返回 `409`，超时不自动回补库存（第 3.5 节口径）。支付完成前该订单对商家端订单查询不可见（按不存在处理），用户端正常可见。
- **店铺可见性**：`GET /api/v1/stores` 仅返回 `OPEN` 与 `TEMPORARILY_CLOSED` 店铺；`CLOSED` 店铺对顾客隐藏（新注册店铺初始 `CLOSED`，商家开店后自动可见），与 PRD"已关店=对顾客隐藏、临时闭店=可见但暂停接单"一致。种子数据 `m004` 演示 `TEMPORARILY_CLOSED`（休息中可见不可下单），保证首页固定 5 家可展示商家。
- **库存冲突错误码**：加购与下单的"商品库存不足"统一返回 HTTP `409` + `code=40901`（此前误用 `40001`），`details` 说明库存上限。
- **优惠配置边界**：`GET/PUT /api/v1/merchant/promotions` 当前仅保存配置，不影响订单结算金额；"优惠统一计价"扩展由小组正式选定后，再接入下单计价并在本节回写金额快照的优惠字段（PRD 7.4 计算顺序）。
- **并发口径**：内存实现的全部仓储读写统一以 Repository 实例为单一监视器（对应未来数据库的事务与行锁）；商家概览 `GET /api/v1/merchant/overview` 的 `orderCount`/`salesAmount` 只统计已支付订单。
