## 1. BUG-20260914-003 公开页整页刷新后加购被误判未登录，跳登录页且不发起请求

| 字段 | 内容 |
| --- | --- |
| 模块/页面 | 用户端 · 商家详情页 `frontend/user-h5/src/views/user/StoreDetailView.vue:381`（`onAdd`）、会话状态 `src/stores/sessionStore.ts`、路由守卫 `src/router/index.ts:219` |
| 严重程度 | **P1**（P0 主链路「浏览 → 加购 → 下单」被打断；可重新登录绕过）——建议值，以测试联调同学确认为准 |
| 是否阻塞 P0 | 阻塞复现路径；首页点入不触发，刷新/深链进入才触发 |
| 前置数据 | 会话有效的登录态（服务端 `JSESSIONID` 仍在，`GET /user/api/v1/cart?storeId=m002` 返回 200）；购物车含 m002 商品 |
| 复现步骤 | 1. 打开 `http://82.157.137.114:4001/user/login`，用 `13800000001/123456` 登录；<br>2. **整页刷新**商家详情页（或直接打开深链 `…/user/stores/m002`）；<br>3. 点商品「香辣鸡腿堡」的「+」加购 |
| 实际结果 | 提示「请先登录」并跳转 `/user/login?redirect=/stores/m002`；**加购请求根本没有发出**（网络日志中该次点击前后无任何 `/api/` 请求），购物车数量不变 |
| 期望结果 | 服务端会话有效时加购成功（登录态恢复后按 PATCH/POST 走购物车接口）；未登录才引导登录 |
| 根因 | `onAdd` 只读客户端 `sessionStore.isLoggedIn`；而 `sessionStore` 仅在 **`meta.auth` 路由**由守卫调用 `checkLogin()`（`GET /me`）恢复。商家详情页是公开页（`meta` 无 `auth`），整页刷新后客户端恒为「未登录」——与服务端会话实际状态不一致。同一文件 `:178`（收藏）、`:435`（去结算）同样只读 `isLoggedIn`；`CouponView`/`MemberView`/`FavoriteListView`/`OrderListView` 均先 `await checkLogin()`，商家详情页三处未做 |
| 证据 | ① 点击加购后 URL 变为 `/login?redirect=/stores/m002`，同一时刻 `fetch /user/api/v1/cart?storeId=m002` **200**（证明会话有效）；② 商家详情页加载期间的请求清单为 `/stores/m002`、`/stores/m002/categories`、`/stores/m002/products`、`/cart?storeId=m002`——**没有 `/me` 探活**；③ 对照：连续 6 次整页打开 `/stores/m002` 均停留在该页（导航本身正常，缺陷由「点击加购」这一步触发） |
| 建议修复 | 三处登录判断前先 `await sessionStore.checkLogin()`（与其余页面同口径），或在应用启动时统一探活一次；修复需先补失败用例（`test:` 先行），覆盖「公开页整页加载后加购不被拦」 |
| 责任人 | 用户端负责人（成员B（用户端），`TODO-USER-114`） |

## 2. BUG-20260914-004 消息中心：通知接口失败连带丢弃真实会话列表

| 字段 | 内容 |
| --- | --- |
| 模块/页面 | 用户端 · 消息中心 `src/views/user/MessageCenterView.vue:53`（`loadAll`） |
| 严重程度 | **P2**（消息模块非 P0 主链路；但在当前线上版本下 19 条真实会话对用户完全不可见，且无任何错误提示）——建议值 |
| 前置数据 | 演示账号 u001 有 **19 条真实会话**（`GET /user/api/v1/conversations` → HTTP 200） |
| 复现步骤 | 1. 登录后打开 `http://82.157.137.114:4001/user/messages` |
| 实际结果 | 页面显示「暂无消息」，会话一条不显示；网络日志显示 `GET /me/notifications` 与 `/me/notifications/unread-count` 均 **404**（`40401 接口不存在`），`GET /conversations` **200 / 19 条** |
| 期望结果 | 通知接口不可用时仍展示会话列表（或以局部错误态提示通知加载失败），不得把可用数据一并丢弃 |
| 根因 | `loadAll()` 用 `Promise.all([listNotifications(), listConversations()])`：任一失败即整体抛出 → `catch` 把两个列表都留空 → `isEmpty` 为真 |
| 证据 | 对照实验：把 `/me/notifications` 拦截为 200 空列表后，`isEmpty` 变为 false（说明会话数据已拿到），证明「显示暂无消息」由通知接口的失败连带导致 |
| 建议修复 | 改为 `Promise.allSettled` 或各自独立 try/catch，会话区独立渲染；补失败用例（通知 404 时会话仍渲染） |
| 责任人 | 用户端负责人（成员B（用户端），`TODO-USER-115`）；后端侧 `/me/notifications` 实现见批次④ `TODO-BE-006` |

## 4. 附：分类商家列表页在真实后端的行为（正面结论 + 一处已知缺口）

| 项 | 实测 |
| --- | --- |
| 入口 | 商家详情店名旁「同类商家 ›」→ `/user/category/c101?name=主食`（标题「主食」） |
