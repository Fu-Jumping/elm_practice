## 00:45 修复：线上支付 500（计价金额未带舍入模式）——P0 阻塞

> 触发：负责人「为什么现在服务暂时不可用，支付不了」。线上后端 `PricingService` 抛未捕获异常 → 全局兜底 500 →
> 用户端显示「服务暂时不可用」，确认订单/支付链路不可用。

### A. 进度事实

- **现象定位**：用户端并无「服务暂时不可用」文案，该串来自后端 `GlobalExceptionHandler.java:51` 的兜底
  （`ApiResponse.error(50000, "服务暂时不可用，请稍后重试")`）——即**后端抛了未捕获异常**，不是服务器宕机。
  探活确认服务本身正常：`4001/user/` 200、`/user/api/v1/stores` 200、`pm2 elm-backend` online 无异常重启。
- **根因（后端日志精确到行）**：`PaymentService` 无关，是**计价**——
  `java.lang.ArithmeticException: Rounding necessary`
  `at com.elm.practice.service.PricingService.price(PricingService.java:70)`
  `at com.elm.practice.service.OrderService.preview(OrderService.java:165)`
  `at com.elm.practice.controller.OrderController.preview(OrderController.java:18)`
  即**确认订单页的计价预览接口** `POST /api/v1/orders/preview`（该接口为线上 d11c1f0 版本新增，本地 main 当时还没有）。
- **机制**：`PricingService` 全类 10 处 `BigDecimal.setScale(2)` **未带舍入模式**；当金额小数位超过两位即抛
  `Rounding necessary`。现场触发值：会员 95 折作用于**无会员价商品的商品小计**，如 19.50 × 5% = 0.975、11.50 × 5% = 0.575。
  因为取决于购物车金额，表现为**"有时候能付、有时候不能"**；订单里全是"有会员价"的商品时不触发（会员价与会员折扣不叠加）。
- **修复**：补 `import java.math.RoundingMode`，10 处 `setScale(2)` 全部改为 `setScale(2, RoundingMode.HALF_UP)`，
  与仓内既有写法（`RequestUtil`、`ExtensionService`）一致；类注释口径同步。安全性论证：修复前凡**需要舍入**的调用必定抛异常，
  故 HALF_UP 不会改变任何曾经通过的结果，只是把异常路径变成正确取值。
- **TDD 红绿（R8：服务器测试库 `elm_practice_test`）**：
  - 红端（仅测试代码）：新增 `TC-PRV-008`（19.50 → 折扣 0.98）→ `Tests run: 5, Failures: 0, Errors: 1`，
    失败即 `ArithmeticException: Rounding necessary`
  - 绿端：→ `Tests run: 5, Failures: 0, Errors: 0 / BUILD SUCCESS`
  - 环境：服务器上从 pm2 运行中的 `elm-backend` 读取 `DB_HOST/DB_USER/DB_PASSWORD` 传入 mvn（口令不入库、不打印）
- **发布**：本次是 P0 阻塞、不能等完整发布流程，故在**线上正在运行的发布目录** `elm-20260915-d11c1f0/backend` 内直接改源码
  → `mvn -B -DskipTests package` 重建 jar（37217188 字节，00:40）→ `pm2 restart elm-backend` →
  健康检查 `127.0.0.1:4000/api/v1/stores` 200。**未动 nginx、未动其他项目进程。**
- **线上复验**：`POST /api/v1/orders/preview` 修复前 500、修复后 **200**；构造修复前必挂的用例（无会员价商品 11.50）→
  返回 `memberDiscountAmount: 0.58`（11.50×5%=0.575 HALF_UP）、`total: 17.92`，与断言一致。
- **需要收口（重要）**：后端修复是**打线上发布目录 + 重建 jar** 的方式生效的，**不是 release.py 正式发布**；
  代码已提交到 main（见下），但**下次谁用 release.py 从旧 tag 发布会覆盖该 jar**——需从含本次修复的提交重新发布一次。
  同一现象已两次出现（用户端热更新 + 本次后端热修），建议在交叉验收后统一重发一版收口。
- **未做的事**：未改 `docs/record/daily/**`；未改 `docs/testing/缺陷跟踪表.md`（写权归测试联调同学，本 P0 建议由其登记）；
