- **根因（线上抓包实证，非推断）**：`POST /api/v1/ai/stream-chat` 每个 token 发一帧 `data:<token>`，**换行 token 落成同一事件内的多条空 `data:` 行**。按 text/event-stream 规范，一个事件的数据 = 其内部各 `data:` 行的值以 `\n` 连接后的结果。原 `ai.ts` 的实现**按行拆、把每行 `data:` 当独立分片、并直接丢弃空值分片**（`if (piece === '' …) continue`），于是换行事件整帧被丢；又因 `line.slice(5).replace(/^ /, '')` 把**属于 token 本身的空格**当字段分隔符剥掉（后端 SSE writer 并不加分隔空格），空格 token 也一起丢。渲染层 `utils/aiReply.ts` 本身正确（首页欢迎语那种本地常量能正确出 4 个块），坏的是流式解析。
- **真实帧证据（线上抓包节选；行间的「空行」即 cat -A 观察到的换行位置）**：

  ```
  data:：
  （空行）
  data:
  data:
  （空行）          ← 两条空 data 行同属一个事件 → 事件数据为 "\n"
  data:-
  （空行）
  data: **
  （空行）
  data: ·
  （空行）
  data:            ← 冒号后**一个空格** = 一个空格 token（不是字段分隔符）
  （空行）
  ```

  同一段流分别用两种解析还原：「正确 SSE 语义」得 **8 个换行**且结构为「一句话 + 3 条 `- **菜名 ¥价格 · 店名**` + 2 段收尾」；「原实现」得 **0 个换行**。

  2. `qtyOf()` 用 `find` 只取**首条**购物车行；而契约 §3.4 规定同一商品的**不同规格是不同行** → 即使抛开渲染条件，跨规格时数量也统计不全。
- **改动**：新增 `totalQtyOf()`（按 `productId` 跨行求和）；在价格右侧、`+` 按钮左侧渲染 `已加购 N` 徽标。**只给数量反馈、仍不给增减控件**（规格商品的增减继续在规格弹层/购物车弹层内完成，PRD 850 行口径不变）。
- **一个易踩的坑（已规避并在代码里注释）**：该徽标必须放在步进器 `v-if` **之前**。若插在步进器与其 `v-else` 的 `+` 按钮之间，会截断 `v-else` 链，使 `+` 按钮改为挂在徽标的 `v-if` 上——规格商品加购后会**失去 `+` 按钮**。
- **TDD 红绿**：新增用例 `SKU-5`（替身用有规格商品 `p107` 双人分享套餐）——**红端**：选完规格提交后断言 `product-added-p107` 存在 → 失败（正是负责人描述的现象）；**绿端**：修复后该断言与"购物车行数/数量一致"断言同时通过。
