用途：集中记录当前 PRD 基线（`docs/PRD.md`）中仍需要课程负责人补充、确认或制作的内容，尤其是课程最新安排、后端技术路线和全流程图。本文件是待办与输入清单，不代表对应功能已经完成；系统行为与接口规则以 PRD 和 `docs/backend/后端接口契约.md` 为准。

## 1. 使用方式

- 完成一项后，把状态改为 `已提供`/`已确认`，填写文件路径、链接或明确答案；无法立即确认的保留 `待定`，不要写进 PRD、报告或答辩。
- 状态取值：`待补充` / `待确认` / `已确认` / `已提供` / `不需要` / `后置`。
- 原始课程资料尽量保留原件或截图；确认后的 PRD 图片放 `docs/prd-assets/**` 对应子目录，不覆盖既有文件。

## 4. 必须补画的全流程图（VIS）

这些是 PRD、报告和答辩必须使用的系统说明图，不是普通页面截图；风格与当前 PRD 图片一致（白底、中文清晰），同时保留可编辑源文件或 Figma 链接。

### VIS-001 全流程产品结构图（待补充；建议文件名 `product-structure-fullstack-v3.png`）

六层结构：①用户端：账号、浏览搜索、商家商品、购物车、地址、订单、评价、消息、资产；②商家端：账号、概览、订单、商品/分类/规格、店铺、优惠、评价、消息、统计；③前端公共能力：路由、Pinia、Axios 适配、Mock/real、响应归一化、设计规范；④后端服务：认证、商家商品、购物车、地址、订单事务（库存、状态同步属已选 P1 扩展能力）；⑤数据库：用户、商家、商品、购物车、地址、订单、明细和扩展表；⑥工程交付：测试、联调、部署、报告、PPT、演示脚本。
验收：前端、后端、数据库和交付关系一眼可读；不把"后端接口预留"当系统终点；不出现未选定的 P2 模块。

### VIS-002 系统技术架构图（待补充；建议文件名 `system-architecture-v3.png`）

必须包含：用户/商家浏览器；Vue 3 + Vite、Vue Router、Pinia、Axios；前端服务层（端点集中与字段归一化）；Spring Boot（若课程确认 Servlet 则改为 Servlet/Tomcat）；Controller、Service、Repository/DAO；MySQL；Session/Cookie 或最终确认的认证方式；Mock 与 real 模式分支；前端、后端、数据库的独立运行边界。
验收：箭头方向清楚；不画未实施基础设施（微服务、Redis、MQ 等）；技术名称与实际版本一致。

### VIS-003 数据库 ER 图（待补充，需等后端表结构确认；建议文件名 `database-er-v3.png`，横向 ≥1600px）

P0 实体：`user`、`merchant_account`、`store`、`category`、`product`、`product_spec`（或等价规格表/JSON 字段方案）、`cart_item`、`delivery_address`、`orders`、`order_item`；选定 P1 后增加 `promotion/coupon`、`review`、`conversation/message`。每个实体至少显示主键、关键外键、状态字段、金额/库存字段；连线标注一对一、一对多或多对多。
验收：与最终建表脚本完全一致；密码字段不使用明文示例；订单明细包含下单快照。

### VIS-004 全流程泳道图（待补充；建议文件名 `core-flow-fullstack-v3.png`，纵向宽约 1260px）

泳道：用户、用户端前端、Java 后端、MySQL/数据层、商家端前端、商家。三段覆盖：

1. 登录与下单（P0 主线）：登录会话、读取商家商品、购物车、地址、后端计价、事务提交/回滚；库存检查与模拟支付属已选 P1，以虚线支线标注。
2. 商家处理（P0 主线）：商家登录、查询本店订单、用户端重新查询订单状态（P0 下单一 `PROCESSING` 不流转）；接单/制作/配送/完成属已选 P1，以虚线支线标注。
3. 扩展闭环：只画已选定 P1（模拟支付与库存一致性、商家接单与订单状态推进）；评价、优惠、统计、消息等未选定模块不画。

P0 必画异常分支：未登录/越权、价格变化、事务失败、重复请求。
验收：正常路径实线、异常/回滚虚线；数据库写入和回滚可见；不得在现有泳道图上改标题冒充新版本。
