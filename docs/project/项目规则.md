### 1.1 问题记录与缺陷跟踪落盘规则（2026-09-08 负责人拍板）

**背景**：此前问题记录散落在群聊、共享文档、本地归档（`docs/_archive/**`，已 gitignore）与 raw/ 片段中，仓库内查不到正式台账，`docs/testing/缺陷跟踪表.md` 长期为空。2026-09-08 负责人明确：问题记录与缺陷跟踪表**由测试联调同学正式落盘、纳入 Git 跟踪**，作为过程证据与交叉验收依据。

**载体与写权**：

| 产物 | 位置（Git 跟踪） | 写权 | 时机 |
| --- | --- | --- | --- |
| 缺陷跟踪表（唯一正式台账） | `docs/testing/缺陷跟踪表.md` | 测试联调同学（王馨琪） | 发现、修复、回归时逐条更新 |
| 问题记录 / 问题单（明细与证据） | `docs/testing/问题记录/YYYY-MM-DD-<主题>.md` | 发现人起草，测试联调同学收录 | 发现时 |
| 即时留痕 | `docs/record/raw/YYYY-MM-DD/` | 成员与 AI 代理（见 §2） | 每轮工作结束 |
| 汇总口径 | 当日 `docs/record/daily/**` A 表（只写编号或链接） | 次晨汇总智能体 / 组长 | 次日上午 |

**硬约束**：

1. **必须在 Git 跟踪范围内落盘**：正式记录一律放 `docs/testing/**`；不得只发群聊、共享文档、`docs/_archive/**`（已 gitignore）或个人目录。群聊与口头只作通知，不作证据。
2. **编号**：接口/业务缺陷 `BUG-YYYYMMDD-NNN`，展示/页面问题 `SHOW-QA-NNN`，递增且不复用；问题记录文件名与台账编号互相引用。
3. **一条问题在台账必须齐全**：发现日期/发现人、模块/页面、环境与版本、前置数据、复现步骤、实际结果、期望结果、严重程度（P0–P3）、是否阻塞 P0、证据、责任人、测试提交（`test:`）、修复提交（`fix:`）、回归结果、当前状态。
4. **状态流转**：`新建 → 已确认 → 修复中 → 待回归 → 已关闭`；无法复现记 `待补充`，暂不处理记 `延期`，重复记 `重复`；**未关闭的缺陷不得写成已完成**。
5. **修复纪律**：需要改代码的缺陷先补失败测试（`test:`）再修复（`fix:`），红绿两端证据写入台账"回归结果"与 raw/ 片段；不得删除、跳过或放宽原测试。
6. **与 daily 的关系**：台账与问题记录承载明细，daily A 表只写编号或链接（§2 第 7 条）；daily 的写权规则不变（§2 第 2、3 条）。
7. **维护节奏**：测试联调同学在每次缺陷提交/回归后更新台账；组长在 PR 评审与里程碑节点核对；中期验收、功能冻结前、交叉验收前各核对一次。
8. **AI 代理边界**：AI 可代拟条目、整理证据与复现步骤，但编号分配、严重程度、状态流转与关闭结论由测试联调同学确认；不得虚构发现人、复现步骤或回归结果。

**存量迁移**：此前已产出的问题记录（含放在本地归档的清单）由测试联调同学统一迁入 `docs/testing/问题记录/` 并登记台账；`docs/record/raw/**` 中既有缺陷片段保留原位、不改不删。

## 2. 每日工作记录规则（2026-09-01 与负责人确认的执行流程）

**执行方式：成员与 AI 代理只落 raw/ 片段留痕，daily 文件唯一写权归次日上午汇总智能体（或组长在 main 上直接维护）；特性分支与 PR 不得携带 daily 变更（2026-09-05 修订）。**

1. **成员随提交附带记录**（二选一，均计入次日汇总）：
   - 在 Git 提交信息正文追加一行 `记录: <今天做了什么/阻塞什么>`（提交信息仍须符合中文规范）；
   - 或把片段放进 `docs/record/raw/YYYY-MM-DD/` 按天文件夹（首个记录者按需创建；文件名如 `<成员或角色>-HHmm.md` 或 `<成员或角色>-<主题>.md`，格式随意，几行即可）。
2. **代理留痕（2026-09-05 修订）**：AI 代理每次工作结束后，把本次进度事实与 AI 使用点写入 `docs/record/raw/YYYY-MM-DD/` 按天文件夹（文件名 `<成员或角色>-HHmm.md`，内容口径沿用 A 表事实 + B 表 AI 使用点），作为成员确认与次晨汇总的输入；**禁止创建或修改 `docs/record/daily/**` 下的任何文件**。
3. **daily 唯一写权 + 次日上午智能体汇总（2026-09-05 修订）**：`docs/record/daily/YYYY-MM-DD.md` 只由次日上午汇总智能体写入（或组长在 main 上直接维护），输入为前一天全部 Git 提交（提交信息"记录:"行、涉及文件）与 `docs/record/raw/YYYY-MM-DD/` 原始片段，由汇总方独立撰写正式版。raw/ 为永久原始留档：汇总只读取，不清理、不移动；成员忘提交的片段留在原地，随下次提交自然入库。成员发现汇总有出入时向组长反馈修正；**任何人不得在特性分支上写 daily，事后补记一律走 raw/ 片段**。
4. **A 当日进度表**沿用原规则：每人每天有事实可记；"今日完成"写可核查事实（如"购物车 Service 6 个用例全绿（提交 abc1234）"）；"阻塞 / 需要谁配合"没有就写"无"；只记事实和计划，不写情绪评价。
5. **B AI 使用点表**按本文件第 3 节填写。
6. 短会（每 2-3 天一次）前组长只扫"阻塞 / 需要谁配合"列；连续两天无记录的成员短会上优先对齐。
7. 出问题的细节走问题单或缺陷单——**正式落盘位置与维护规则见 §1.1**（缺陷跟踪表 `docs/testing/缺陷跟踪表.md` + 明细 `docs/testing/问题记录/**`，均由 Git 跟踪、测试联调同学维护）；每日记录里只放编号或链接。
8. **Git 硬约束（2026-09-05 新增）**：特性分支与 PR **不得携带 `docs/record/daily/**` 的变更**；PR 评审检查项包含本条（见 `docs/project/小组协作与提交流程.md` §7），发现携带即打回，作者改放 raw/ 片段后再提交。**每日记录的通道只有两条**：提交信息 `记录:` 行与 raw/ 片段；缺陷与问题的正式落盘另走 §1.1（`docs/testing/**`，不属于 daily 通道）。

## 3. AI 使用点记录规则（课程考核要求）

**记录粒度**：记主要使用点，不必逐行；标准是"能向老师说明哪部分参考了 AI 产出、人做了什么审核"。

**类别**（B 表"类别"列取值）：

- 脚手架 / 样板代码（工程骨架、组件模板、配置）
- Bug 修复辅助（定位思路、修复方案）
- 文档初稿（PRD/SRS/契约/说明文档的草拟与整理）
- 原型 / 提示词（Stitch 等设计工具的提示词与界面稿）
- 测试用例生成（测试思路、用例清单）
- 其他

**每条记录的字段**：任务（做了什么）→ 类别 → AI 做了什么 → 人工审核与修改（谁改了什么、如何验证）→ 结果（采纳 / 部分采纳 / 弃用）。

**红线**：

- 无法解释逻辑的 AI 产出不得并入交付；合入前必须有人读懂并验证。
- **业务代码与全部测试代码不得由同一 AI 一次性生成后一起提交**（课程要求"AI 不能既当运动员又当裁判"）；测试标准与异常场景由人设计，细则见 `docs/project/TDD实施规划.md` 第 7 节。
- 不在记录中粘贴密钥、真实账号密码等敏感信息。
- AI 只是辅助，需求判断与验收结论由人负责；"传话筒式"直接搬运 AI 结论写进正式文档前必须人工核实。

**与 Git 留痕关系**（2026-09-06 统一口径）：AI 深度参与产生的提交（生成或修改业务代码、测试代码、文档正文），**必须**在提交信息正文末尾追加一行 `AI协作: <一句话说明>`（提交信息其余部分仍按中文规范）；纯人工小改可只落 raw/ 片段，随次晨汇总进入每日记录 B 表。

**汇总出口**：整理答辩材料时，从 `docs/record/daily/**` 的 B 表汇总出"AI 使用说明"一节，放入课程报告与答辩素材，作为课程要求的溯源证据。

## 4. 里程碑节点的记录动作

- **中期验收（9/8，或顺延 9/9）前**：检查 `docs/record/daily/**` 是否逐日齐全，作为"谁在什么阶段做了什么"的过程证据。
- **功能冻结（9/15）前**：补齐当日记录；冻结后不再有新功能条目，只记验收问题修复。
- **材料归档（第 4 周，具体日期以老师通知为准）前**：汇总 AI 使用点与每日进度，供报告与答辩引用。
