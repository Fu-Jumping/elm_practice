**前提（工程背景）**：单仓库多目录组织——`frontend/user-h5/`（用户端 Vue 3 + Vite + Pinia）、`frontend/merchant-admin/`（商家端 React 18 + Vite + Ant Design 5）、`backend/`（Java Spring Boot + MyBatis，数据库选型待后端确认）。后端测试框架 JUnit 5，用户端 Vitest。关键时间口径：**9/8（或 9/9）进行第一阶段中期验收，P0 基础功能须于 9/7 晚完成并于当晚验收演练**；9/5–9/6 为周末冲刺日（9/5 注册登录/权限与商品分类管理，9/6 购物车与店铺浏览链路）；验收后立即进入第二阶段需求变更。

## 1. 为什么测试先行（课程要求摘录）

以下均为课程要求原文摘录，是本规划的直接依据：

> 今年强制强调**测试先行**。基本要求是：1. 先理解需求。2. 先设计单元测试。3. 明确正常情况和异常情况。4. 再编写业务代码。5. 业务代码通过测试后，才能认为这个功能基本完成。

> 老师特别强调，测试的重要价值就是主动验证这些**异常场景**。

（课程要求以"注册用户"为例，要求不能只测"正确手机号 + 正确密码 → 注册成功"，还要测：手机号只有 10 位、手机号有 12 位、手机号包含字母、手机号已经存在、密码长度不足、密码不符合复杂度要求。这六条已完整纳入第 5.1 节用例矩阵，编号 TC-ACC-002~007。）

> 第二周注意事项：2. 不能只测试正常情况，要重点测试异常情况。

关于业务规则归属：

> **前端校验：主要为了用户体验。** **后端校验：真正保证业务规则。**"手机号是否已经注册"这种需要查询数据库的逻辑，更必须放在后端。

因此本规划的用例矩阵以后端 Service/接口层为主战场，前端用例只覆盖归一化、状态逻辑和核心交互。

关于交叉验收与自测的边界（课程要求）：

> 不能因为第三周有人帮你测试，就不做自己的测试。1. 自己开发过程中必须做**单元测试**。2. 项目内部也应该进行必要的集成测试。3. 交叉验收时，其他组主要从完整系统角度做集成和验收测试。

关于 Git 可见性（课程要求）：

> 必须持续提交，不能前两周仓库为空，最后一天一次性上传。不能通过强制覆盖等方式把历史提交记录抹掉，因为老师会通过仓库记录观察项目过程和个人贡献。

即：测试先行不只是开发习惯，还必须能从提交历史里**被看见**（第 3 章）。

## 2. TDD 工作流（红-绿-重构）

### 2.1 什么是一个"功能单元"

- 后端：一个接口的一条业务规则，或一个 Service 方法。例如"注册时重复账号返回 409"是一个单元，"整个注册模块"不是。
- 用户端：一个 store action、一个 normalizer/工具函数，或一个核心组件交互（如购物车弹层减到 0 移除该行）。
- 商家端：一个表单校验规则或一个状态标签渲染分支。

### 2.2 标准循环（每个功能单元）

| 步骤 | 动作 | 完成标志 |
| --- | --- | --- |
| ① 红 | 从第 5 章矩阵挑本单元用例，写测试并运行。失败原因必须是"功能未实现"（断言不匹配、404 等），不是测试自身写错 | 测试红；首次失败的关键输出贴入当日 `docs/record/daily/` A 表 |
| ② 绿 | 写**最小**业务代码让测试通过，不预做矩阵之外的功能 | 测试全绿 |
| ③ 重构 | 消除重复、抽取公共校验；重跑本单元及受影响用例保持绿 | 无行为变化，测试仍绿 |
| ④ 提交 | `test:` 提交（红）在前，`feat:` 提交（绿）在后（见第 3 章） | `git log` 可查顺序 |

约束：

- 重构改动原则上并入本次 `feat:` 提交（`分工与里程碑安排.md` 的类型前缀集合为 `feat:` `fix:` `test:` `docs:` `chore:`，无 `refactor:`）；确需独立提交时用 `chore:` 并在提交信息正文说明。
- 禁止先写实现再补测试提交；禁止用无断言的测试凑数；禁止用 `@Disabled` / `skip` 让红测试"看起来绿"。
- 提交粒度：一个功能单元一批（红 + 绿），当天收工前提交，不攒批。

### 2.3 "功能完成"的门槛（Definition of Done）

一个功能单元满足以下全部条件才算完成：

1. 该单元在用例矩阵中的用例（正常 + 至少 1 条异常）全部执行且通过——**异常用例全绿 + 业务代码通过测试**；
2. 该单元实际会出现的错误码语义（400/401/403/404/409）至少各有一条用例覆盖；
3. 响应符合统一结构（`code`/`message`/`data`，错误返回 JSON 而非 HTML 错误页）；
4. Git 中 `test:`（红）提交早于对应 `feat:`（绿）提交；
5. 原有测试没有被删除、跳过或放宽断言；
6. 当日 `docs/record/daily/` A 表有一行记录（含提交号）。

模块级门槛：该模块矩阵内全部编号用例通过，且按接口契约第 8 节模板填写至少一条模块联调记录。

## 3. Git 证据规范

### 3.1 规则

依据 `docs/project/分工与里程碑安排.md` 第 3 节与课程要求：

- 每人用自己的账号提交，禁止代提交、禁止最后一天整包上传。
- **TDD 证据靠提交顺序体现：同一功能的测试类先提交（允许红），实现后提交（绿），不事后补测试提交。**
- 提交信息用中文，类型前缀用英文：`feat:` `fix:` `test:` `docs:` `chore:`。
- 禁止 force push 或任何抹除历史的操作；改代码走分支 + PR，review 规则见 `小组协作与提交流程.md`。
- AI 深度参与产生的提交，按 `docs/project/项目规则.md` 第 3 节在提交信息正文末尾追加 `AI协作: <一句话说明>`。

### 3.2 提交序列示例（符合本项目业务，中文信息 + 英文前缀）

序列一：账号模块（9/5，后端 A）

```text
test: 用户注册失败测试：10位/12位/含字母手机号、重复注册、密码过短（预期红）
feat: 实现注册接口字段校验与重复账号 409 拦截
fix: 修复密码长度下限校验边界（5 位密码未被拦截）
```

序列二：购物车模块（9/6，后端 B）

```text
test: 购物车异常用例：数量为0、加购超库存、未登录返回401（预期红）
feat: 实现购物车加入、同商品数量合并与删除接口
fix: 修复同商品重复加购未合并数量的问题
```

序列三：订单创建模块（9/7，后端 B + 前端主力）

```text
test: 订单创建失败测试：库存不足、店铺关闭、地址归属校验（预期红）
feat: 实现订单创建事务与商品、地址快照保存
test: 购物车数量合并与金额归一化测试（用户端 stores/normalizers）
feat: 用户端确认订单页接入创建订单接口与金额回显
```

说明：每对 `test:`→`feat:`构成一次红-绿循环；`fix:`提交是回归发现的缺陷修复，修复时若有新用例，先补 `test:` 再 `fix:`。老师课堂示例（`feat: add user registration` / `test: add invalid phone tests` / `fix: reject duplicated users`）体现的就是这个粒度；本项目在此基础上额外要求 `test:` 早于 `feat:`。

### 3.3 老师会查什么（对应自查方式）

| 老师关注点（课程要求） | 本项目自查方式 |
| --- | --- |
| 持续真实提交，不是最后一天整包上传 | `git log` 按日期分布检查；每日记录 A 表逐日可对 |
| 每人用自己的账号、贡献真实可查 | `git log --author=<本人账号>`（分工文档第 4 节答辩自查项） |
| 历史不被抹掉 | 禁止 force push；分支合并保留历史 |
| 测试先于实现 | `git log --follow <测试文件路径>` 首次提交早于对应实现提交 |
| 能否解释自己提交的代码 | 答辩前按分工文档第 4 节"每人贡献自查"过一遍 |
| 原有测试没有被无故删除 | 冻结前对比矩阵用例数与现存测试数；PRD 埋点方案的 TDD 行要求"测试先于实现，原有测试没有被无故删除" |

## 4. 测试分层与工具

### 4.1 后端（JUnit 5，`backend/src/test/java`）

| 层 | 内容 | 工具 | 说明 |
| --- | --- | --- | --- |
| Service 单元测试 | 业务规则：注册校验、金额计算、状态机、资源归属 | JUnit 5 + Mockito 打桩 DAO | 不连数据库，跑得快，是第 2 章循环的主战场；400/409 类规则在此层先红 |
| 接口集成测试 | Controller + 统一响应结构 + 会话/权限 | MockMvc（首选，同进程快）或 TestRestTemplate | 断言 HTTP 状态码 + `code`/`message`/`data` 结构；401/403/404 与 Session 相关用例主要在此层验证 |
| 数据层 | 建表脚本可重复执行、种子数据 | 测试环境数据库（见下） | 验证事务回滚、唯一约束 |

**数据库测试环境取舍建议**（最终由后端同学确认，记录到第 10 章）：

- 方案 A：H2 内存库 MySQL 兼容模式——快、无外部依赖；风险是 H2 与 MySQL 方言差异可能掩盖真实 SQL 问题。
- 方案 B：本地 MySQL 测试库执行真实建表脚本——真实，但环境依赖重。
- 建议路径：Service 单测一律不碰库；接口集成测试先用 H2 起步，若建表脚本大量使用 MySQL 特有语法（如 `ON DUPLICATE KEY`、JSON 字段函数）则切换到方案 B。无论哪种，测试数据在各用例内自建，用例之间不依赖执行顺序。

### 4.2 用户端（Vitest，`frontend/user-h5`）

| 优先测 | 内容 | 说明 |
| --- | --- | --- |
| services/normalizers | 后端字段 → 页面字段归一化：缺字段不产生 `undefined` 展示、金额两位小数、时间 `yyyy-MM-dd HH:mm:ss` | 纯函数，最易测、收益最高 |
| stores（Pinia） | 购物车同商品数量合并、合计金额、跨商家隔离提示、订单状态到展示文案的映射 | 状态逻辑不等价于后端规则，只测前端职责部分 |
| 工具函数 | 手机号/密码/11 位电话校验、格式化 | 与后端规则保持同一口径，测试数据从契约推导 |
| 核心组件交互 | 购物车弹层（步进加减、减到 0 移除、售罄灰化）、确认订单页（提交禁用条件、金额以后端为准） | 用 @vue/test-utils + jsdom；**只挑这两个核心交互，不做全页面组件测试** |

不设覆盖率百分比指标（见第 10 章）。

### 4.3 商家端（React Testing Library，`frontend/merchant-admin`）

轻量覆盖即可，不追求页面全覆盖：

- 表单校验：商品表单必填、价格 ≥0、库存非负的提示是否出现（Vitest + RTL + jsdom）；
- 状态渲染：店铺三态（OPEN/CLOSED/TEMPORARILY_CLOSED）与售罄标签的文案和语义色正确渲染；
- AntD 组件行为本身不重复测试。

### 4.4 证据留痕

- 测试运行结果以命令输出/测试报告为证据，关键节点（首批失败测试、模块全绿、冻结前回归）在每日记录 A 表引用；
- 后端构建与核心测试通过是 PRD 7.18 的交付要求；用户端、商家端 `npm run build` 与后端构建在 9/7 全链路联调和 9/15 冻结前各跑一次并留日志。

## 5. P0 模块测试用例矩阵（核心章节）

使用说明：

- 本矩阵是**代表性用例清单**，不是穷举；执行中发现的缺陷必须回补成用例（先 `test:` 后 `fix:`）。
- "层"取值：后端单测 / 后端集成 / 双端 / 前端（用户端或商家端）。
- 错误码依据 `docs/backend/后端接口契约.md` 第 1.3 节：`400` 格式/必填/范围不合法，`401` 未登录或 Session 失效，`403` 角色不匹配或无权访问，`404` 资源不存在或归属不符时按安全需要统一返回不存在，`409` 重复注册/状态冲突/库存金额版本已变化，`500` 未预期错误。
- 契约未逐条固定状态码的少数场景（店铺关闭加购、有商品分类删除等）在表中标"口径 SRS 固化"，SRS 定稿后回填，不得凭空写码。
- 带有"（P1 扩展）"的用例对应已选扩展（模拟支付 + 库存一致性、商家订单推进），在 P0 用例全绿后再实施。

## 7. AI 与测试的边界

课程要求的规则与老师引语：

> 不允许的做法：……4. 让 AI 同时完整生成业务代码和全部测试代码。
>
> > AI 不能既当运动员，又当裁判。
>
> 如果 AI 自己生成注册业务代码，然后再让同一个 AI 针对自己的实现生成测试，它很可能写出一套天然能够通过自己代码的测试，因此人必须参与测试标准和异常情况的设计。

本项目执行细则：

1. **禁止**"AI 生成业务代码 + 同一 AI 生成全部测试"，也禁止测试代码与业务代码由同一代理一次性生成后一起提交。物理上必须拆成 `test:`（红）与 `feat:`（绿）两次提交，且用例清单（正常/异常场景与断言口径）先于代码设计确定。
2. **人负责测试标准**：第 5 章矩阵和变更单里的"新增测试清单"由模块负责人与测试联调同学人工确定后，才允许借助 AI 落地测试代码。异常场景（错误码、边界值）的选取必须有人的判断，不能由 AI 从实现反推。
3. **AI 可辅助的范围**：测试类骨架、测试数据工厂/fixture、Mock 样板、断言模板等脚手架性内容；生成的测试必须逐条可解释，经人审核修改后才能合入。
4. **记录**：AI 使用点按 `docs/project/项目规则.md` 第 3 节记入每日记录 B 表（类别取"测试用例生成"）；AI 深度参与的提交在提交信息末尾追加 `AI协作: <一句话说明>`。
5. **红线**：无法解释逻辑的 AI 产出不得并入交付；答辩被抽查到测试用例时，作者本人必须能说明该用例为什么这样设计。

## 9. 需求变更时的测试流程

阶段 2 需求变更（**9/8 第一阶段中期验收后立即接收**；若验收顺延至 9/9，则在验收当天接收）同样执行"先补失败测试锁定新行为，再最小实现并回归"的红-绿流程；变更登记、影响分析与归档由组长组织。变更各步骤与 TDD 的对应关系：

| 变更流程步骤 | TDD 对应 |
| --- | --- |
| 先写新增测试（红） | 红：失败测试**锁定新行为**，提交早于实现 |
| 最小实现（绿） | 绿：只改影响分析列出的范围，新测试全过 |
| 回归测试 | 全部既有测试重跑通过；失败项修复后重跑并记录 |

补充约束：

- 原有用例不得因变更被删除或放宽断言；行为确实变化的用例在变更单中说明后修改，而不是静默改测试。
- 变更新增的用例同步登记进第 5 章矩阵（编号沿用模块前缀，在变更单中标注对应 CHG 编号），保证矩阵始终是全组用例的唯一索引。
- 禁止趁机重构与本次变更无关的代码；想改的记入"冻结后重构清单"。

## 10. 本规划的局限与待定项

以下事项如实标注，待小组确认后回填本文，不作为已定事实：

1. **数据库测试环境选型**：H2 兼容模式与真实 MySQL 测试库的取舍（第 4.1 节建议路径）待后端建仓、建表脚本成形后确定；数据库本身选型（MySQL 或 PostgreSQL）也是 PRD 标注的待确认项。
2. **后端框架精确版本**：Spring Boot/MyBatis 版本待后端确认（PRD 待确认项），MockMvc/TestRestTemplate 的最终选择随版本定。
3. **仓库组织口径**：本规划按"单仓库多目录（`frontend/user-h5/`、`frontend/merchant-admin/`、`backend/`）"编写；该口径已于 2026-09-01 依据课程要求"每组必须建立一个代码仓库"确认，并在运行说明等文档中固化；各端工程独立、独立进程，不影响本文的测试分层与用例矩阵。
4. **前端组件测试深度**：只做第 4.2/4.3 节列出的核心交互，不做全页面组件测试；深度是否加大视 9/8 中期验收结果决定。
5. **覆盖率不设硬指标**：不以百分比覆盖率为完成标准，以 PRD 目标 G3"TDD 过程完整率"（核心任务留有需求分析、测试先行、首次失败、实现通过和回归记录）和矩阵执行率为准。
6. **个别异常场景错误码未逐条固定**：店铺关闭加购、有商品分类删除、不满足起送条件等场景的 `400`/`409` 归属需在 SRS 固化后回填矩阵，当前标注"口径 SRS 固化"。
7. **矩阵为代表性清单**：不是全量穷举；缺陷回补用例、交叉验收反馈的问题都会追加编号，矩阵版本随文档更新。
