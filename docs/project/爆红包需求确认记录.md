## 2. 第 1 轮问题（爆红包 / 开红包，共 10 条）

### 问题 1：这个界面从哪里进入？
问题说明：入口决定它挂在哪个路由、是否新增页面、是否需要登录判断，也决定演示时你从哪个页面开始操作。
可选方案与对比：
- 方案A：首页活动区入口（点“天天爆红包”筛选标签或运营卡片进入全屏开红包页）
  - 具体做法：首页现有装饰标签变成可点入口，进入独立全屏页
  - 主要好处：演示路径最短、首页本来就最拿得出手
  - 潜在风险：首页装饰标签一旦可点，就要保证它不再是“假入口”
  - 适用情况：想让老师第一眼就点到
- 方案B：红包页内的“开红包”按钮（进入弹层）
  - 具体做法：`10-个人中心/04-红包` 页顶部加一个开红包按钮，弹层里拆红包
  - 主要好处：与现有红包模块同页，数据关系最自然
  - 潜在风险：演示时要先点进“我的 → 红包”，路径长
  - 适用情况：想强调与红包模块的完整性
- 方案C：支付成功后弹层（支付成功页出现“拆红包”）
  - 具体做法：支付成功 → 弹层 → 拆开 → 入账
  - 主要好处：业务闭环最真实（下单得红包）
  - 潜在风险：依赖支付链路先稳定
  - 适用情况：想讲“下单即得”的故事
- 方案D：进入用户端自动弹（仅演示时触发）
  - 具体做法：启动页后或首次进入首页时弹出
  - 主要好处：最抓眼球、无需操作
  - 潜在风险：每次进入都弹会烦，且容易与启动页动画冲突
  - 适用情况：只在现场演示用一个开关控制
  你的回答：方案A、方案B都做，从首页活动区入口进入红包页，在红包页才能开红包

### 问题 2：红包从哪里来（发放规则）？
问题说明：这决定**要不要新增“发放 / 领取记录”表和接口**，是本模块能不能在 9/15 前收口的关键。

  - 主要好处：可重复演示、测试可断言、风险最低
  - 潜在风险：没有“随机惊喜”感
  - 适用情况：时间紧、要稳

  - 具体做法：加“领取记录”表（用户 + 日期 + 金额），后端校验当日是否已领

  - 潜在风险：要新表 + 新接口 + 边界用例（约 +0.5 天）
  - 适用情况：愿意为“可变现的业务规则”多花半天

  - 具体做法：支付成功回调里生成一张待领红包
  - 主要好处：与订单联动最真实
  - 潜在风险：依赖支付链路与订单事务，改动面大
  - 适用情况：支付模块先收口后
- 方案D：纯演示不落库
  - 具体做法：只做动效与结果展示，不入账、不可在下单时使用
  - 主要好处：1 天内能做出来
  - 潜在风险：**不算红包模块的一部分**，没有数据库与接口证据，不加分
