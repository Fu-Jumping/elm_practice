## 2. 总体架构

```
elm_practice/（单仓库）
├── frontend/
│   ├── user-h5/          用户端移动 H5（Vue 3 + Vite + Pinia + Vue Router + Axios），端口 5173
│   └── merchant-admin/   商家端桌面后台（React 18 + Vite + AntD 5），端口 5174（建议，见 9.7）
├── backend/              Java 后端，http://127.0.0.1:4000，接口统一 /api/v1 前缀
└── docs/
```

- **通信**：RESTful + JSON；两端是同仓库里两个独立工程、独立进程，互不包含对方代码。
- **认证**：按契约采用服务端 Session Cookie（登录后 `Set-Cookie`，前端请求携带 `credentials`），**前端不保存 token、不接收后端下发的身份 ID**。此方案已于 2026-09-02 由组长确认维持，后续不再变更。前端判断登录态的方式是启动/守卫时调用探活接口（用户端 `GET /api/v1/me`、商家端 `GET /api/v1/merchant/me`），401 即未登录。
- **统一响应**：`{ "code": 0, "message": "success", "data": ... }`，`code=0` 为业务成功；错误结构含 `details` 字段；服务端错误一律返回 JSON 不返回 HTML（契约原文）。前端按此结构显式处理，不做"猜测式"归一（见 7.4）。
- **接口适配层（两端强制）**：页面层不直接拼接接口路径、不直接解析原始响应。请求发送、响应拆包、字段归一化统一收敛在 `services/`（见 3.3 / 4.4）。
- **Mock / real 双模式**：环境变量三件套（契约已定名）——
  - `VITE_API_MODE=mock|real`：mock 走工程内 `mocks/` 演示数据，real 走真实接口；
  - `VITE_API_BASE_URL`：real 模式接口地址（联调口径 `http://127.0.0.1:4000/api/v1`（2026-09-10 统一））；
  - `VITE_MOCK_FALLBACK`：real 请求失败是否自动回退 mock，联调阶段必须为 `false`。
  - 两工程必须提供 `.env.example`，任何人克隆后不问人即可跑起来。
- **开发节奏**：契约先行 → 按 `mocks/` 演示数据开发页面 → 后端接口就绪后切 real 联调 → 9/7 晚关闭 `VITE_MOCK_FALLBACK` 全链路联调。演示分级以 P0 主线默认 Mock 演示为口径，因此 **mock 数据必须离线可跑、不依赖外部服务**。
- **跨域与 Cookie 备注**：契约已允许 5173 及 Vite 顺延端口跨域。联调时若发现 Cookie 不随请求携带，按顺序检查：① axios 是否开启 `withCredentials`；② 后端 CORS 是否 `Allow-Credentials` 且返回具体 origin；③ Cookie 的 `SameSite` 属性。兜底方案是改用 Vite `server.proxy` 把 `/api` 代理到 4000（同源、只改 vite.config 与 baseURL，业务代码零改动）。

## 3. 用户端 user-h5 架构（Vue 3）

### 3.1 目录结构

在 PRD §仓库结构基础上组织，`utils/` 与 `composables/` 为建议增补项（评审通过后同步 PRD）：

```
frontend/user-h5/src/
├── main.ts               入口：注册 Pinia/Router、全局错误处理、引入样式
├── App.vue               根组件：路由出口 + 页面切换过渡
├── router/               路由表 + 全局守卫
├── layouts/              MainLayout（含底部导航）/ BlankLayout（登录注册等无底栏页）
├── views/user/           页面级组件，与 PRD 6.2–6.11 页面一一对应（本期新增页面清单见 3.2）
├── components/           可复用组件（基础组件 Base 前缀；弹层、步进器、商家卡等）
├── composables/          useXxx.ts 组合式函数（建议增补）
├── stores/               Pinia，每域一个文件
├── services/
│   ├── http/             axios 实例 + 拦截器（见 3.3）
│   ├── api/              按业务域拆分的接口函数 + endpoints.ts 单点维护路径
│   └── normalizers.ts    契约字段归一化（金额、时间、枚举→文案）
├── mocks/                按业务域拆分的演示数据（对齐契约字段与联调种子数据）
├── constants/            枚举与常量（订单状态、营业状态、分类等，与后端枚举对齐）（建议增补）
├── styles/               tokens.css 设计令牌 + base.css（单一来源，禁止多文件重复定义）
├── utils/                纯工具函数（校验、格式化，测试主战场）（建议增补）
├── assets/               静态资源
└── tests/                Vitest 测试（对齐 TDD 规划 §4.2）
```

- **不引入 UI 组件库**：用户端承担 exact 复刻（见 `UI复刻经验与执行约定.md`），必须完全掌控 DOM 与样式；通用交互组件（弹层、步进器、Toast）自建。设计令牌以 `docs/design/设计系统-用户端.md` 为源落在 `styles/tokens.css`，品牌橙 `#ff5a1f` 单一来源。
- **复刻像素但类名语义化**：对齐复刻约定 3.2——保留设计稿 DOM 层级与视觉，类名用语义命名，不搬运设计工具导出的无语义类名。

### 3.2 路由与守卫

- 路由表集中在 `router/index.ts`，全路由懒加载 `component: () => import(...)`；每条路由带 meta 约定：

| meta 字段    | 用途                                                |
| ------------ | --------------------------------------------------- |
| `title`    | 页面标题（document.title）                          |
| `tab`      | 是否显示底部导航（`layouts/MainLayout` 据此渲染） |
| `auth`     | 是否需登录；守卫据此拦截                            |
| `priority` | P0/P1/P2，与 PRD 页面矩阵对应，验收与演示排期用     |

- 全局守卫 `router.beforeEach`：`meta.auth` 且未登录 → 跳登录页并带 `redirect` 参数，登录成功后回原页（PRD 7.x 要求登录失效保留地址跳转后回原流程）。
- 未登录可浏览首页/商家列表/商家详情/搜索结果（PRD 7.15 口径）；加购与结算、地址、下单与支付、订单（含取消、订单跟踪、配送信息只读展示）、评价、消息、收藏、会员权益、红包、系统设置需登录。
- 提供显式 404 页，不静默重定向首页。
- 底部导航固定"首页/消息/订单/我的"（PRD），作为 `MainLayout` 的组成部分统一实现，禁止各页自带底栏。

### 3.3 请求层（services/http + api + normalizers）

```
页面 → stores（action）→ services/api/auth.ts（按域函数）→ services/http（拦截器）→ mocks/ 或 后端
```

- **axios 单实例**：`baseURL` 读 `VITE_API_BASE_URL`；`withCredentials: true`（Session Cookie 随请求携带）；timeout 10s。
- **请求拦截器**：防重复提交——同 `method+url+参数` 的进行中请求用 `AbortController` 取消旧的；**不**注入 Authorization 头（Session 认证无 token）。
- **响应拦截器**：
  1. HTTP 层：`401` → 清空前端会话态、跳登录（带 redirect）；`403/404/409/500` → 统一 toast 契约 `message`；
  2. 业务层：`code !== 0` → toast `message` 并 reject；`code === 0` → 直接 `return data`，业务层只拿干净数据；
  3. 防御性检查仅限"响应必须是 JSON"（契约规定服务端错误必返 JSON，若收到 HTML 说明联调配置错误，按环境错误提示，不做内容嗅探兜底）。
- **api 按域拆文件**：既有域 `auth / store / product / cart / order / address / review(P1) / message(P1)`；**本期新增域（2026-09-09 决议）**：`search`（搜索与排序分页：综合排序＝销量优先、评分次之，距离取种子固定 `distanceKm`，`page`/`size` 默认 1/10）、`favorite`（商家收藏）、`member`（会员权益）、`coupon`（红包）、`notification`（通知）、`promotion`（优惠配置与计价明细）、`cancellation`（取消订单）、`delivery`（配送单）、`upload`（图片上传，定稿口径见 9.14：商品图 1 张、评价图最多 3 张、单张 ≤2MB、jpg/jpeg/png/webp，存 `backend/uploads/` 经 `/uploads/**` 访问，越权 `403`）、`statistics`（经营统计）。路径集中在 `endpoints.ts`，与契约逐条对齐；`api/index.ts` 桶导出，页面只见 `orderApi.getList()`。**新增域在契约补齐对应章节（PRD §9 已列契约缺口）后方可进入实现与测试，前端不得自行定义路径或字段。**
- **normalizers.ts 显式映射**：按契约字段名一一转换（金额保留两位小数、时间 `yyyy-MM-dd HH:mm:ss`、状态枚举→文案/色调），缺字段给确定默认值，禁止多键名试探式解包。此文件是单测必测对象（TDD 规划 §4.2）。
- **mock 与 api 同构**：mock 模式下同一套 api 函数返回 Promise（模拟网络延迟 200–500ms），页面代码对 mock/real 无感知；mocks 数据字段严格按契约写，并用 `docs/backend/后端联调验收用例.md` 的种子数据（13800000001、merchant-a 等），保证演示与联调用同一套数据口径。

### 3.4 状态管理（Pinia）

每域一个 store，统一模式：`state` 含 `loading / error`；action 调 api 并返回结果；视图负责提示。首期 store 划分：

| store                  | 职责                                               |
| ---------------------- | -------------------------------------------------- |
| `sessionStore`       | 当前用户信息、登录态探活（`GET /me`）、登录/退出 |
| `catalogStore`       | 店铺列表/详情、分类、商品（浏览域数据）            |
| `cartStore`          | 购物车行数据与合计（服务端购物车，见下）；**本期新增规格行**：同一商品不同规格按 `cartLineId` 分行，行内带规格摘要与价差，合计仍以后端返回为准 |
| `orderStore`         | 订单列表/详情/下单/模拟支付/取消/配送状态查询      |
| `addressStore`       | 地址簿 CRUD 与默认地址                             |
| `messageStore`（P1） | 通知与会话列表、**未读数**（本期实现：用户端 `unread` 与商家端 `merchantUnread` 分别记录，进入会话标记本会话已读后刷新角标） |

- **购物车为服务端购物车**：加购/减购/改数量即调 `/cart` 系列接口，前端不自算总数（契约已有该组端点，后端为唯一真源）；store 保存行数据与派生合计用于展示；按商家隔离、同商品合并由后端保证，前端展示层校验只做体验兜底。**前端不持久化业务数据**（购物车、订单都不落 localStorage）；会话恢复依赖 Session Cookie + 启动探活。
- **本期新增域的状态收敛（2026-09-10 负责人拍板定稿，见 9.13）**：评价、收藏、会员、红包、优惠、统计等新增域以"页面级请求 + 组件本地状态"为主，不新增常驻 store；只有消息未读（`messageStore`）与购物车规格行（`cartStore`）需要跨页共享，按上表实现。
- 订单状态流转：状态机在后端。前端每个操作（支付、取消等）= 调接口 → 重新拉取；状态→文案/色调/步骤条映射集中在 `utils/orderStatus.ts` 的映射表，禁止页面散落魔法数字。用户端文案映射按 PRD 7.6 定稿：`PENDING_PAYMENT` 待支付、`PENDING` 待接单、`COOKING` 制作中、`DELIVERING` 配送中、`COMPLETED` 已完成（未评价时展示"待评价"）、`CANCELLED` 已取消；**支付成功即 `PENDING`（待接单），`PROCESSING` 仅作 P0 阶段状态保留、不作为支付后状态**（后端现行 `markPaid` 写 `PROCESSING` 为偏差，待按定稿修正）。订单详情可做 15–30s 轮询（模拟支付倒计时场景），不引入 WebSocket。

### 3.5 移动端适配与性能

- **vw 适配**：`postcss-px-to-viewport-8-plugin`（PostCSS 8 维护版），`viewportWidth: 390`（PRD 设计宽 390、最小 320）；`selectorBlackList` 视需要排除第三方类。不使用 lib-flexible（官方已声明弃用）。
- `viewport-fit=cover` + `env(safe-area-inset-bottom)` 处理底栏安全区。
- 验收视口：320 / 360 / 375 / 390 / 430（复刻约定 3.3 口径）。
- 性能：全路由懒加载 + `scrollBehavior` 回顶；列表图片 `loading="lazy"`；首屏骨架屏（loading 转圈仅用于行内小操作）；不做虚拟列表等超配优化。
- 商家详情页"左分类右商品"联动优先用原生 CSS 滚动 + `IntersectionObserver` 实现，不引入 better-scroll（少一个库，滚动容器策略见复刻约定 2.7）。复合滚动页先设计滚动容器与 sticky 层级再动手。
- 页面切换动画只做 opacity 淡入淡出，不位移页面壳（复刻约定 2.11）。

### 3.6 支付与定位（均为模拟口径）

- 支付：支付页 + 支付成功页 + 支付失败页（本期新增，PRD 7.5）+ 待支付 15 分钟倒计时 + 重复支付幂等提示，不接第三方支付。倒计时用时间戳差值计算而非累减，避免后台切换误差；支付失败页"重新支付"必须先查询订单当前支付状态再决定跳转，不得直接重发支付请求。
- 定位：首页定位栏用默认城市 + 固定坐标常量，不接地图 SDK；地址管理走地址簿 CRUD。

## 4. 商家端 merchant-admin 架构（React 18 + AntD 5）

### 4.1 目录结构

```
frontend/merchant-admin/src/
├── main.tsx              入口：ConfigProvider 主题 + App 包裹 + RouterProvider
├── router/               集中路由表 + RequireAuth 守卫
├── layouts/              BasicLayout（Sider 菜单 + Header 顶栏 + Content）
```

- **状态管理：不引入状态库**（README §2 留待 9/3 定稿，本文给推荐）：全局态只有"登录态 + 店铺营业状态"，用 React Context（AuthContext / StoreStatusContext）承载；页面数据用组件本地 state + 请求即可，CRUD 页面间无共享业务状态。评审通过后同步 README §2。

### 4.2 AntD 主题与全局框架

- `ConfigProvider theme={{ token: { colorPrimary: '#ff5a1f' } }}`，hover/active 色板由算法派生；组件内取主题值用 `theme.useToken()`。
- **官方坑必须遵守**：`message`/`Modal` 静态方法不继承 ConfigProvider 主题——全项目用 `<App>` 组件包裹 + `App.useApp()` 获取 `message`/`modal` 实例，禁止直接调静态方法。
- `BasicLayout`：Sider 内 `Menu` 用 `items` 数组（不用已废弃的 children JSX 写法）；**菜单项 `key` 直接用路由 path**，`selectedKeys={[location.pathname]}`，点击 `navigate(key)`；菜单固定**九项平铺、不分组**："运营概览/订单/商品/分类/优惠配置/评价管理/消息/数据统计/店铺设置"（PRD 6.12–6.17；**2026-09-09 决议后九项全部为本期实现**；规格维护在商品页内、**评价管理与评价回复合并为一页（列表 + 回复抽屉）**、聊天详情在消息页内，均不单独占菜单项）。Header 放营业状态胶囊 + 账号 + 退出。
- 提供全局 ErrorBoundary，兜底渲染错误并提示刷新。

### 4.3 列表页标准模式（自建 SearchTable 模板）

商家端最高频页面是"筛选 + 表格 + 分页"，建一个约 100–150 行的项目级 `SearchTable` 模板组件（Form 搜索区 + Table 受控 + `usePaging` hook 管页码），每个列表页 30 行内完成，**不引入 ProComponents**（学习成本 > 收益，见 9.5）。

- 订单列表：状态页签（全部/待接单/制作中/配送中/已完成）切换即改查询参数重查；操作列按钮按状态渲染。
- 状态流转：每次操作（接单/出餐/完成）= 调 `PATCH /merchant/orders/{id}/status` → 刷新列表 + 更新行内 Tag；**前端不自造状态机**；`409` 统一提示"数据已变化，请刷新后重试"（契约文案）。
- 筛选变化时页码重置为 1；删除后当前页为空回退上一页；搜索防抖。
- 表单：统一 `Form.useForm()` + `onFinish`；默认值放 `initialValues`，运行时改值用 `setFieldsValue`；Switch 用 `valuePropName="checked"`；放弃编辑需确认弹窗（PRD 7.12）。
- 商品表单字段严格按 PRD 7.12（名称、分类、说明、价格≥0 两位小数、库存非负整数、上架开关，以及会员价、标签、图片与规格字段）；**2026-09-09 决议后图片上传、规格与会员价均为本期实现项，表单字段全部出现**，图片走上传组件（定稿口径见 9.14：商品图 1 张、单张 ≤2MB、jpg/jpeg/png/webp，存 `backend/uploads/` 经 `/uploads/**` 访问），规格区块在表单内编辑并保存 `specOptions/priceDelta`。

### 4.4 请求层

与用户端同模式（单实例 + withCredentials + 拦截器统一错误 + api 按域），差异仅：接口域为 `/api/v1/merchant/**`、登录探活用 `GET /merchant/me`、401 统一跳商家登录页。mock/real 环境变量与用户端同名同义，两工程各自维护 `.env`。

## 7. 既往实践提炼（工程侧红线）

以下模式来自既往同类前端实践的复盘，均为一般化描述，按"现象 → 根因 → 正确做法"组织（UI 复刻侧教训见《UI复刻经验与执行约定》§2，此处不重复）。**两端实现自检时逐条对照。**

### 7.1 超大页面组件 + 组件层空心化

- 现象：单页面文件 1000–2000+ 行，共享组件只有个位数，页面间靠复制粘贴。
- 根因：没有在开工前约定组件粒度与"页面只做编排"的分层。
- 正确做法：页面组件负责编排（取数 + 布局），可复用视觉块下沉 `components/`；单文件超过约 300 行即触发拆分讨论。

### 7.2 写死兜底数据伪装成真实数据

- 现象：接口失败或字段缺失时页面显示写死的商家名、评分、统计数字，看起来"能跑"实则数据为假。
- 根因：用兜底默认值掩盖接口问题；无"演示数据必须显式标注"的纪律。
- 正确做法：缺数据就显示 loading/错误/空态，不造数据；演示数字一律来自 `mocks/` 并在展示场合声明"演示数据"（课程展示口径）。

### 7.3 前端自建"后端"

- 现象：用 localStorage 模拟订单状态机、跨标签同步，业务规则写进前端。
- 根因：图演示效果绕过后端；职责边界未定。
- 正确做法：业务规则与状态机只属于后端（本项目契约亦如此约定）；mock 只负责"给定请求返回数据"，不含规则推理。

### 7.4 猜测式响应归一

- 现象：请求层对响应结构做多键名试探、字符串嗅探（如检测 HTML 字符串猜状态），换后端即碎。
- 根因：代码先于契约编写，归一层靠猜。
- 正确做法：契约先行；normalizers 按契约字段显式映射；响应异常按环境配置错误处理，不做内容嗅探兜底。

### 7.5 路由无守卫、会话不持久

- 现象：受保护页面未登录可直达；刷新后登录态丢失。
- 根因：只声明了角色 meta 没有消费它的守卫；登录态存内存。
- 正确做法：全局守卫消费 meta（3.2 / 4.1）；登录态以服务端 Session + 探活为准，页面刷新后自动恢复。

### 7.6 请求层"伪统一"

- 环境变量开关骨架是对的，但每个 api 函数内重复 if-else 切 mock，且成功码靠字符串猜测。
- 正确做法：mock/real 切换收敛在 http 层一处（3.3 同构方案），api 函数只写业务请求；成功判断只认契约 `code=0`。

### 7.7 双份实现并行维护

- 现象：同一业务存在"静态演示版"与"真实工程版"两套代码，改一处漏一处。
- 根因：演示需求与工程实现没有合一。
- 正确做法：演示需求由 mock 模式承载（本架构的 mocks/ + VITE_API_MODE 即为此设计），仓库内不存在第二套页面实现。

### 7.8 工具链缺位

- 现象：无测试、无 lint、无路径别名（全项目 `../../`）、无代理配置、无 `.env.example`。
- 正确做法：这五件在 **9/3 初始化当天**随脚手架落地（见 §8 Checklist），不后补。

### 7.9 保留并沿用的骨架

既往实践中验证有效、本文明确沿用的模式：双模式请求层骨架、api 按域拆分 + endpoints 单点、store 统一 `loading/error` 模式、路由 meta 约定驱动 UI、设计令牌单一来源、状态→文案映射表、mock 按域分文件、白名单式 .gitignore。

## 10. 风险与需前后端对齐项

- **商家端订单接口优先级疑似错位（2026-09-02 已移交后端 A 设计定夺）**：商家端订单列表/详情为 PRD P0 页面，但契约将 `/merchant/orders` 系列标注为 P1 条件启用。该接口的交付顺序与设计已交由后端 A（王嘉悦）在 9/3 开工评审裁决并回写契约（见契约第 5 章设计移交注记）。前端商家端订单页照常按 Mock 开发，不阻塞；仅真实联调节点（9/7 晚前）需等后端 A 的定稿结论。
- Session Cookie 的 `SameSite`/`Secure` 属性与 CORS `Allow-Credentials` 需后端在联调前配置到位（见 §2 备注），建议列入联调 Checklist 第一项。
- 时间格式、金额单位的格式化函数两端各自实现，验收时用 `docs/backend/后端联调验收用例.md` 数据交叉核对，防止两端展示不一致。

**2026-09-09 决议连带需对齐项（前端侧）**：

- **范围扩张与收口节奏**：除平台管理员外全部 P1/P2 纳入本期。用户端以 PRD §6.1 扩展服务 13 页为基础，另含搜索结果、订单跟踪、取消订单确认、配送信息/状态等页面；商家端新增 7 页与规格维护、图片上传。开发量约为原计划的 2–3 倍，须按"接口 + 数据库 + 测试 + 页面"四类证据分批收口，未收口模块一律写"本期实现（待开发）"。**分批顺序（9/10–9/14，2026-09-09 决议）**：①优惠与统一计价 → ②取消与配送 → ③评价与回复 → ④消息 → ⑤搜索 → ⑥收藏/会员/红包 → ⑦规格 → ⑧图片上传 → ⑨统计；每批以"接口 + 数据库 + 测试 + 页面"四类证据收口。
- **契约缺口（PRD §9 已列）**：搜索分页、收藏、会员、红包、通知、优惠计价、取消订单、配送单、图片上传和统计聚合接口，需契约新增章节后才进入实现与测试；前端先按 `mocks/` 开发，不自行定义路径与字段。图片上传的数量/大小/类型参数已于 2026-09-09 定稿（见 9.14），其余接口章节仍待契约补齐。
- **无设计稿页面**：取消订单确认页、配送信息/状态页（用户端）与商家端新增 7 页没有设计稿或代码导出，按设计系统令牌与 PRD 字段列新建；验收不以截图比对作结论，也不得用通用卡片简化（复刻约定 2.2）。
- **消息未读与客服边界**：用户端 `unread` 与商家端 `merchantUnread` 分离记录，刷新时机（进入会话即已读、列表轮询）需前后端对齐；平台客服仍不在范围，"联系商家"仅指订单用户与该订单商家的会话。
- **订单与配送状态映射**：前端 `utils/orderStatus.ts` 需补齐用户端文案映射 `PENDING_PAYMENT`（待支付）/`PENDING`（待接单）/`COOKING`（制作中）/`DELIVERING`（配送中）/`COMPLETED`（已完成，未评价时展示"待评价"）/`CANCELLED`（已取消），以及配送状态（PENDING_DELIVERY/DELIVERING/DELIVERED）映射，取值与契约一致；**支付成功即 `PENDING`（待接单），`PROCESSING` 仅作 P0 阶段状态保留**（后端现行先置 `PROCESSING` 为偏差，待按定稿修正）；取消仅 PENDING_PAYMENT/PENDING 可操作，按钮显隐以后端返回状态为准，前端不自行判断合法性。
- **支付与倒计时幂等**：待支付 15 分钟倒计时、重复支付与重复状态推进的提示文案需与契约错误码（含 409）对齐，避免两端提示不一致。
- **金额与优惠口径**：按 PRD 7.4 固定顺序由后端计价——实付 = 商品小计 − 满减 − 新客立减 − 红包 − 会员折扣 + 配送费（默认 ¥3.00，店铺可配、未配置按 0） − 配送费优惠 + 打包费（¥2.00），且不小于 0；订单新增金额快照字段 `deliveryFee`；确认订单页与订单详情金额明细为**四行**（商品小计 / 打包费 / 配送费 / 实付金额），前端 `expectedTotal` 仅作提示、以后端结果为准；**配置了 `memberPrice` 的商品按会员价计价、不再叠加会员折扣，未配置会员价的商品才应用会员折扣**；优惠配置结构（`promotions` 扩列 `new_user_amount`/`free_delivery_threshold`/`member_discount`，满减阶梯新表 `promotion_tiers`）与演示数值（满 20 减 2、满 40 减 5、新客立减 3 元、免配送费门槛 30 元、会员 95 折、一单一红包）须与契约、种子数据和测试用例同步。
- **统计口径**：经营统计只统计数据库中的有效订单并注明查询范围，不得用固定演示数值冒充经营结果（PRD 7.17 与 §8 记录边界）。
